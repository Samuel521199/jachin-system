## 1. 泳道视角：三阶段 × 四职能

### 1.1 三大阶段（横向阶段）

| 阶段 | 侧重 |
| --- | --- |
| **立项 / 评审** | 明确需求目标与范围，完成立项与评审闸门 |
| **开发 / 验收** | 美术与技术并行交付，经历评审 / 自测 / 联合验收与产品验收 |
| **上线发布** | 发布评审、冒烟、班车（分批）上线；上线后数据跟踪与复盘 |

### 1.2 产品（Product）

**职责概要**：明确需求目标；完成 PRD；组织需求评审及后续宣讲对齐；需求跟进；组织验收与发布相关评审；上线后总结复盘。

**典型步骤**：

- **需求文档**：产出并维护需求说明载体
- **需求评审**：PRD 宣讲、目标对齐、开发前准备
- **需求跟进**：开发期内持续跟进需求落地
- **产品验收**：对照需求验收交付物
- **发布评审**：上线前闸门
- **冒烟测试**：上线前快速验证主干可用性

阶段叙事（与示意图一致）：先明确需求目标与目的并完成立项与需求评审 → 进入功能开发（含美术评审/验收、技术自测与最终产品验收）→ 上线发布后进行数据跟踪与复盘分析。

### 1.3 美术（Art）

**职责概要**：美术需求评估；需求设计；美术评审；美术开发与交付；美术验收；物料整理便于接入版本。

**典型步骤**：

- **确认需求**：与产品 / 相关方对齐美术范围与标准
- **美术评审**：方案 / 风格 / 关键节点评审
- **美术开发**：制作与迭代资产
- **美术验收**：交付前美术侧收口
- **物料整理**：交付给研发 / 运营的成套物料

说明（进度表指南摘抄）：实践中可采用「美术、后端先行，前端搭框架」等协作节奏（以具体项目约定为准）。

### 1.4 技术（Technology）

**职责概要**：技术方案评估；需求开发；环境部署；技术自测与验收；班车发布。

**典型步骤**：

- **确认需求**：评估可行性、拆分技术任务并与产品对齐
- **技术开发**：实现与集成
- **环境部署**：测试 / 预发 / 生产等环境就绪
- **技术自测验收**：研发侧质量收口
- **班车发布**：按发布窗口合入 / 上线

### 1.5 市场 / 运营（Marketing / Operations）

**职责概要**：对齐需求背后的业务目标；同步市场与运营计划；关注数据同步与投放侧优化。

**典型步骤**：

- **确认需求**：理解功能对获客 / 留存 / 投放的影响
- **制定运营计划**：活动、物料、节奏与资源协调
- **数据同步，投放优化**：上线后联动数据与投放策略迭代

### 1.6 跨职能收口（示意图中的「末端大块」）

- **联合验收**：美术–技术–产品联合验收
- **上线链路**：发布评审 → 冒烟测试 → **班车发布**（分批上线窗口）
- **总结复盘**：需求上线后的效果跟踪、数据复盘与归因优化

## 2. 闭环视角：任务流转总图（摘要）

下图逻辑对应常见的「调研 → 立项 → 拆解 → 多轨并行 → 测试验收 → 上线 → 再调研」闭环（与第二张流程示意图一致）。

### 2.1 立项与拆解

1. **调研**
2. **立项提案**（可由调研与市场 / 运营侧诉求共同触发）
3. **立项评审**
   - **否**：进入备选 / Backlog / On Hold，可择机重新提案
   - **是**：进入 **需求拆解**
4. **需求拆解** → **需求宣讲 / 评审**
   - **未通过**：回到拆解细化
   - **通过**：并行进入三条主干之一（或组合）：
     - **产品路径**：沉淀 **产品任务表**
     - **开发路径**：经 **开发评估** → **开发任务表**
     - **设计路径**：经 **美术评估** → **设计任务表**

### 2.2 执行与同步

- **产品任务表** 与 **日常需求收纳** 联动（增量需求持续汇入主线）。
- **开发任务表** 与 **设计任务表** 之间需保持同步（示意图中以「同步」强调进度对齐）。
- **开发自测**：未通过则回到开发任务表修正；通过后进入 **联调**。

### 2.3 测试、发布与回流

1. **联调**：研发与设计成果集成调试；可与日常需求收纳并行演进。
2. **产品验收表**：承载验收清单 / Bug 清单等，随验收推进更新。
3. **发布评审**：未通过回到联调；通过后进入上线链路。
4. **环境部署**：典型链路为「部署测试环境 → 部署生产环境 → **发布上线**」。
5. **需求发布**：上线且验收通过后闭环本轮需求。
6. **回流**：发布完成后流程回到 **调研**，开启下一轮迭代或新项目探索。

## 3. 《任务流转》— 产出规范（概要版）

### 3.1 立项提案（产品）

- 市场调研论据充分
- 明确数据目的与指标
- 需求说明可采用「左文右图」或「左图右文」，便于对齐认知
- 计划说明含资源配置、成本预估、效果预估
- **讨论尽量前置**，避免积压到宣讲阶段才暴露分歧

### 3.2 需求文档 PRD（产品 / 市场 / 运营）

- 配备流程图 / 参考视频 / 配图，降低理解成本
- **需求拆分与优先级**：除「新游戏级」完整工程外，其余需求倾向 **短平快**，优先级 **动态更新**
- **美术需求尽量前置**：尽早参与立项，明确业务目的
- 表述 **简洁、精准、流程化**，减少开放式选择题式描述

### 3.3 产品任务表 / 需求池（产品 / PM）

- **每日更新**：条目、责任人、状态、优先级、进度、评审节点、上线节点、冲刺周期等
- 创建结构遵循目标拆解：**epic → story → task → task1**（大需求尽量拆细）
- 支持部门给出排期后，持续对齐 **开发任务表**、**设计任务表** 的执行进度

### 3.4 开发任务表 / 设计任务表（开发 / 美术）

- 需求确认后及时刷新：冲刺周期、责任人、进度、完成节点等
- 同样遵循：**epic → story → task → task1**
- 开发 / 美术可在 **当月产品需求池** 中认领与核对需求
- 开发侧应能通过 **设计任务表** 追踪美术交付进度

## 4. 《项目进度表使用指南》— 进度表与拆解体系

### 4.1 阶段叙事（与时间轴）

| 维度 | 立项 / 评审 | 开发 / 验收 | 上线发布 |
| --- | --- | --- | --- |
| **目标** | 明确需求目标与目的；完成立项与需求评审 | 功能开发；含美术评审/验收、技术自测及最终产品验收 | 上线发布；数据跟踪；复盘分析 |
| **典型里程碑** | 需求文档、需求评审（宣讲与对齐） | 需求跟进、多职能并行交付 | 联合验收；发布评审；冒烟；班车上线 |
| **收口** | — | 产品验收 | 总结复盘（效果跟踪、数据归因） |

### 4.2 进度表字段释义（整理版）

PDF 中原表为宽表并伴随排版拆字，此处按语义归纳为常用字段集群（名称以你们多维表 / 表格模版为准）。

| 字段族 | 含义与填写要点 |
| --- | --- |
| **需求（Requirement）** | 按 **Epic → Story → Task** 结构录入；新建 Story 后再按部门 / 岗位拆 Task |
| **优先级（Priority）** | 可选 **P0–P3** |
| **冲刺（Sprint）** | 通常 **按周** 为一个版本迭代周期 |
| **版本目标（Version / Goal）** | 阐明当周冲刺目标 |
| **预期 / 目的（Expectation / Purpose）** | 标明 Story 的预期业务目的与当前状态（如提升留存、优化中、待验收等） |
| **进度（Progress）** | Story 整体状态 |
| **负责人 / 参与人** | Story 或 Task 的责任人与参与者；多人可并列 |
| **启动日期（Start）** | **产品**：立项（内审）通过后可视为开动参考点 |
| **评审日期（Review）** | **产品**：需求评审通过日 |
| **验收日期（Acceptance）** | **技术**：开发完成；**美术**：交付前端素材前的评审通过日（评审需产品、技术参与）；**美术验收**：早于或与产品验收并行（可与技术自测验收同步）；**产品**：整体验收通过日 |
| **预计交付 / 实际交付** | 美术、技术各自的预计与实际交付时间点 |
| **预计上线 / 实际上线** | 对外发布窗口与实际发布时间 |

**填写规范**：提倡全员自主填写、及时更新；或由负责人 / 组长填报。**日期类字段**在周粒度场景下可约定统一锚点（例如每周周一）以减少口径漂移——具体以团队模版为准。

### 4.3 层级结构：`Epic → Story → Task`

**总原则**：命名与拆分遵循 **产品 PRD 中的 glossary（术语表）**，避免私自造词导致跨角色理解不一致。

#### Epic（史诗）

- **层级**：最大、最粗的需求粒度
- **特点**：业务价值大，常跨多个迭代 / 版本；颗粒度过粗无法直接开发
- **作用**：归类与规划方向

#### Story（故事）

> PDF 原文标题拼写为「Stroy」，此处按业界惯例写作 **Story**。

- **层级**：中等颗粒度，迭代交付的核心单元
- **特点**：从用户视角描述功能；通常可在一次 Sprint 内完成、测试并上线；具备明确验收标准
- **推荐句式**：
  > 作为 **【某角色】**，我想要 **【某功能】**，以便 **【实现某价值】**。

#### Task（任务）

- **层级**：最小执行单元
- **特点**：把 Story 拆成具体工种工作（开发 / 测试 / UI 等）；用于估点与进度跟踪
- **示例**：前端实现注册页布局；后端实现手机号验证码接口；测试编写并执行用例

**格式提示**：Task 建议带上 **Epic** 字段前缀（PDF 中以类似 `Texas Holdem Plus-` 的前缀举例），避免海量任务检索困难。

### 4.4 小结（拆解口诀）

| 层级 | 一句话 |
| --- | --- |
| **Epic** | 大业务模块 → 太大，不能直接开工 |
| **Story** | 可交付的小功能 → 迭代里真正做出来的需求单元 |
| **Task** | 具体干活的工种拆分 → 产品 / 美术 / 开发 / 测试的执行项 |

## 5. 如何使用本文档

- **对齐节奏**：先用 **§1 泳道** 与各职能负责人对齐「谁在什么阶段干什么」。
- **对齐产出**：用 **§3** 检查立项 / PRD / 三张任务表是否满足最低规范。
- **对齐表格**：用 **§4** 统一优先级、冲刺、验收与上线字段口径，并按 Epic / Story / Task 拆解落地。
- **对齐闭环**：用 **§2** 对照端到端是否存在「跳过宣讲 / 跳过联调 / 无回流调研」等结构性缺口。
