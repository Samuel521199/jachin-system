# 项目进度每日快照

本目录由 **`mcp:atom_pmo_lark_doc`**（`operation=sync`）按 **拉取日期** 自动创建子文件夹 `YYYY-MM-DD/`，写入从飞书 Wiki 嵌入的 **K11 多维表** 导出的 Markdown（与 `sync_bi_project_context` 同源逻辑）。

默认包含三张表（可在 `atom_pmo_lark_doc` 配置中覆盖 `wiki_urls` 或关闭 `use_k11_default_tables`）：

1. **K11 需求池** — 需求描述、Sprint、优先级、责任人、需求/开发状态等  
2. **K11 项目进度** — 任务树、优先级、Sprint、执行人、起止日期、预计人天等  
3. **美术/设计任务** — 任务、Sprint、设计责任人、排期等  

每次同步会在当日目录内生成若干 `.md` 及 `00_SYNC_MANIFEST.json`，并额外生成 **`00_K11_TABLES_INDEX.md`** 说明本次种子链接与表含义。

## 项目进度表使用说明

以下内容整理自《项目进度表使用指南》，与 Wiki / 多维表中 **项目进度** 的填写与协作方式一致，便于对照本目录导出的快照理解字段含义。

### 端到端流程（目标与时间视角）

- **立项（内审）评审 → 技术方案评估 → 需求开发 → 环境部署 → 技术自测验收 → 上线发布**（技术侧原子环节）。
- **美术需求评估 → 需求设计 → 美术评审 → 美术验收**（美术侧环节）。
- **需求评审**：需求文档、需求评审；**明确需求目标**，完成 PRD 撰写，**需求跟踪及验收发布**，**总结复盘**；PRD 宣讲、目标对齐、开发前准备。
- **需求开发**：美术、后端先行，前端搭框架。
- **上线发布 / 联合验收**：对应「立项/评审」「开发/验收」阶段；**美术–技术–产品联合验收**；**发布评审 → 冒烟测试 → 班车上线**。
- **总结复盘**：需求上线效果跟踪、数据复盘归因。

### 各角色关注点（摘要）

| 角色 | 典型工作 |
| --- | --- |
| **产品** | 确认需求；制定运营计划；需求跟进、产品验收；发布评审、冒烟测试；需求复盘 |
| **美术** | 确认需求；美术评审、美术开发、美术验收；物料整理 |
| **技术** | 确认需求；技术开发、技术自测验收；环境部署；班车发布 |
| **市场/运营** | 确定需求目的、调研、多方讨论；对齐需求目标；同步市场/运营计划；数据同步、投放归因优化 |

### 字段说明（与表头对应）

填写时 **全员自主、及时更新**，或由 **负责人/组长** 分配后填写；**日期列在周视图中以每周周一展示**；多项需 **负责人或 PM 确认** 后再填。

| 字段（英文档常见列名） | 含义 | 填写说明要点 |
| --- | --- | --- |
| **Requirement** | 需求 | 按层级结构填写：从 **Epic** 往下建 **Story**，再按部门/岗位拆 **Task**。 |
| **priority** | 优先级 | 可选 **P0–P3**。 |
| **Sprint** | 冲刺 | **按周为一个版本迭代周期**。 |
| **Version / Goal** | 版本目标 | 说明本周冲刺目标。 |
| **Expectation / Purpose** | 预期/目的 | 标明 Story 的预期与开发目的（如提升留存、产品优化等）。 |
| **Progress** | 状态 | Story 整体状态（如开发中、待验收等）。 |
| **Person in charge / Participant** | 负责人/参与人 | Story 或 Task 的对应人员；尽量落到单人，多人可填多人。 |
| **Start Date** | 启动日期 | **产品**：立项（内审）通过日。**美术/技术**：需求确认后的开动日期（美术通常早于技术）。 |
| **Review Date** | 评审日期 | **产品**：需求评审通过日。**美术**：提交给前端素材前的 **美术评审通过日**（需产品、技术参与）。 |
| **Acceptance Date** | 验收日期 | **技术**：开发完成后自测。**美术**：美术验收（在产品验收之前，可与技术验收同步）。**产品**：产品整体验收。 |
| **Expected Delivery Date** | 预计交付日期 | 美术、技术、产品验收预计完成日。 |
| **Actual Delivery Date** | 实际交付日期 | 美术、技术、产品 **实际验收通过** 日。 |
| **Expected Launch Date** | 预计发布日期 | 预计上线时间。 |
| **Actual Launch Date** | 实际发布日期 | 实际上线时间。 |

（具体列名以当前飞书多维表为准，上表与官方指南字段一一对应。）

### 需求层级：Epic → Story → Task

- **结构**：`Epic -- Story -- Task`。
- **原则**：遵循产品 PRD 的 **glossary**，避免自定义用词导致信息偏差、不同步。

#### Epic（史诗）

- **层级**：最大、最粗的需求。
- **特点**：业务价值大，常跨多个迭代/版本；过于笼统、无法直接开发；用于 **归类与规划大方向**。

#### Story（故事）

- **层级**：中等颗粒度，敏捷开发的核心单元。
- **特点**：从用户视角描述功能；通常可在 **一个 Sprint** 内完成、测试、上线；有明确验收标准。
- **标准句式**：作为【某角色】，我想要【某功能】，以便【实现某价值】。

#### Task（任务）

- **层级**：最小执行单元。
- **特点**：把 Story 拆成具体工种工作；分给开发、测试、UI 等；用于估工时、跟进度。
- **示例**：前端开发某页面布局；后端写验证码接口；测试编写并执行用例。

#### 层级小结

- **Epic**：大业务模块 → 太大，不能直接落地开发。  
- **Story**：可交付的小功能 → 迭代里真正做的需求。  
- **Task**：具体干活的细分工作 → 产品/美术/开发/测试的执行项。

### 填写注意（Task 与 Epic 关联）

- **Task 须带上 Epic 信息**（或表中要求的 Epic 字段），保证任务可归因到大模块；指南示例为在任务名称或字段中体现形如 `Texas Holdem Plus-` 等 **Epic 前缀/标识**（以你们表结构为准）。
