# Jachin 架构 V2 — Layer 3 单体对标 OpenClaw 的划时代设计

**版本**: 2.0  
**状态**: 设计规范  
**定位**: 重新定义 Layer 1/2/3 职责 — L3 为 **Jachin 执行节点**（单主轴 ReAct，**能力对标** OpenClaw 类单机 Agent），L2 = 权限/记忆/调度，L1 = 平台。

> **2026-04 对齐现行实现**：L3 代码路径为 **`run_agent` 单循环**，并挂载语义层、内联 Critic、Experience RAG 等；**SSOT** 见 **[architecture/JACHIN_HYBRID_AGENT_ARCHITECTURE.md](./architecture/JACHIN_HYBRID_AGENT_ARCHITECTURE.md)**。**现行组件索引（MCP/后台/zombie/桌面）** 见 **[architecture/CURRENT_SYSTEM_ARCHITECTURE.md](./architecture/CURRENT_SYSTEM_ARCHITECTURE.md)**。本文档为历史设计长文，**不随每次代码变更更新**；与 [../ARCHITECTURE.md](../ARCHITECTURE.md) 冲突时以全局规范与代码为准。本文中「OpenClaw」均指**对标物**，非 Jachin 产品名。

## 〇、核心变化摘要

```
┌─────────────────────────────────────────────────────────────────────────────────┐
│  Layer 1：平台（注册与管理若干用户主账号）                                          │
│  • 平台主账号：管理平台内部内容、其他用户主账号，与 L2/L3 无关                      │
│  • 用户主账号：在平台注册，每个用户主账号管理其自己的 L2 + L3 系统                  │
└─────────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│  Layer 2：子账号 + 权限 + 记忆 + 梦境 + 调度 + API Key 管理                         │
│  • 子账号在 L2 创建，权限控制 L3 节点、L2 部分记忆与资源                             │
│  • 管理 API Key（存储、下发密文给 L3），不代理 L3 的推理请求                         │
│  • 记忆存储、梦境优化、L3 协同调度                                                  │
│  • 可与 L3 同机部署                                                                │
└─────────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        ▼
┌─────────────────────────────────────────────────────────────────────────────────┐
│  Layer 3：Jachin L3（单主轴 ReAct + 多 Skill/MCP + 本地记忆；能力对标 OpenClaw 类）   │
│  • 本地持有密文 Key，发送请求时解密为明文后自行调用外部 API                         │
│  • L2 只管理 Key，不代理请求；L3 自己发请求处理问题                                 │
│  • 可与 L2 同机部署                                                                │
└─────────────────────────────────────────────────────────────────────────────────┘
```

| 层级 | 旧架构 (v8.0) | 新架构 (V2) |
|------|---------------|-------------|
| **Layer 1** | 云端指挥、舰队、蓝图 | **平台**：注册/管理若干用户主账号；平台主账号管平台内部，与 L2/L3 无关 |
| **Layer 2** | 边缘大脑（Agent + 记忆 + 执行） | 子账号、权限、记忆、梦境、L3 调度、**API Key 管理**（不代理请求）、可与 L3 同机 |
| **Layer 3** | 终端外壳（UI、HITL、感官） | **Jachin L3**：单主轴 ReAct + MCP/Skill；本地密文 Key，解密后直连 API；可与 L2 同机（对标 OpenClaw 类能力） |

**本质**：L1 是平台；用户主账号在平台注册，每个用户管理自己的 L2+L3；L2 只管理 Key，L3 持密文 Key 自行发请求。

## 一、Layer 1：平台

### 1.1 职责定义

Layer 1 是**平台**，负责注册和管理若干**用户主账号**。平台本身有**平台主账号**，与 L2/L3 无关。

| 概念 | 说明 |
|------|------|
| **平台** | Layer 1 作为平台，提供用户注册、登录、多租户能力 |
| **平台主账号** | 管理平台内部内容、其他用户主账号；**不涉及 Layer 2、Layer 3** |
| **用户主账号** | 在平台上注册的普通用户，每个用户主账号管理其自己的 L2 + L3 系统 |
| **子账号** | 子账号**不在** Layer 1 创建，由用户主账号在 **Layer 2** 创建 |

### 1.2 平台与用户主账号关系

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  Layer 1（平台）                                                              │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  平台主账号 (Platform Admin)                                           │   │
│  │  • 管理平台内部内容、其他用户主账号                                      │   │
│  │  • 与 Layer 2、Layer 3 无关                                            │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  用户主账号 (User Main Account) — 若干                                 │   │
│  │  • 在平台上注册/登录                                                   │   │
│  │  • 每个用户主账号管理其自己的 L2 + L3 系统                               │   │
│  │  • 管理自己的 L2 节点、L3 节点、资源、策略                              │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
                                        │
                                        │ 用户主账号登录 L2 管理界面
                                        ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Layer 2                                                                     │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  子账号 (Sub-Account) — 在 L2 创建，归属用户主账号                      │   │
│  │  • 由用户主账号在 L2 管理界面创建                                       │   │
│  │  • 根据权限管理：允许的 L3 节点、L2 上的部分记忆与资源                   │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 1.3 子账号权限模型（在 L2 创建时定义）

| 权限维度 | 说明 | 示例 |
|----------|------|------|
| **L3 节点** | 子账号可使用的 L3 节点列表 | 子账号 A 只能使用 L3-1、L3-2 |
| **L2 记忆** | 可访问的 L2 上部分记忆范围（按 **namespace** 隔离） | 子账号 B 只能读 `customer_service_kb` 命名空间 |
| **L2 资源** | 可使用的 L2 资源（如存储配额） | 子账号 C 限制 10GB 记忆 |
| **Skill 白名单** | 可安装、可调用的 Skill 列表 | 子账号 D 只能用办公类 Skill |
| **任务发布** | 是否可向 L2 发布协同任务 | 子账号 E 只能单机执行 |

### 1.4 数据模型

```
-- Layer 1（平台）
platform_admins (平台主账号，与 L2/L3 无关)
  id, ...

users (用户主账号，在平台注册)
  id, email, name, ...

-- Layer 2 存储
sub_accounts (子账号，在 L2 创建，归属用户主账号)
  id, main_user_id, name, role, permissions_json, created_at

sub_account_permissions
  sub_account_id, resource_type, resource_id, action (read/write/execute/...)
  -- resource_type 枚举见下节
```

### 1.5 sub_account_permissions 的 resource_type 枚举

| resource_type | resource_id 示例 | action | 说明 |
|---------------|------------------|--------|------|
| **service_switch** | `can_coordinate` | allow/deny | 是否允许发布协同任务 |
| **service_switch** | `can_memory_read` | allow/deny | 是否允许读取 L2 记忆 |
| **service_switch** | `can_memory_write` | allow/deny | 是否允许写入 L2 记忆 |
| **service_switch** | `can_keys_read` | allow/deny | 是否允许获取 API Key |
| **service_switch** | `service:coder` | delegate | 服务角色白名单（delegate 时） |
| **l3_node** | `l3-node-id` | keys:read | 该节点可获取 Key（l3_node_ids 白名单） |
| **skill** | `core:fs_read` | execute | 允许调用的 Skill（空=全开，`__none__`=全禁） |
| **skill** | `*` | allow | 技能通配符，允许全部 |
| **memory_namespace** | `customer_service_kb` | read | 允许访问的记忆命名空间（allowed_memory_namespaces） |

**说明**：`memory_namespace` 实现细粒度记忆隔离，子账号仅能读写其 `allowed_memory_namespaces` 列表内的命名空间；未配置时默认允许全部。

## 二、Layer 2：子账号、权限、记忆、调度、API Key 管理

### 2.1 职责定义

Layer 2 是**控制平面 + 记忆平面 + 调度平面 + API Key 管理**，可单机也可多节点集群。

| 职责 | 说明 |
|------|------|
| **子账号创建** | 用户主账号在 L2 创建子账号，定义权限范围 |
| **权限管理** | 校验 L3 请求、子账号权限（L3 节点、L2 记忆与资源） |
| **API Key 管理** | L2 管理 API Key（存储、下发密文给 L3），**不代理 L3 的推理请求** |
| **数据记忆** | 接收 L3 同步的记忆，经梦境优化后存储，供 L3 检索 |
| **梦境系统** | 对记忆进行聚类、去重、融合、冲突消解 |
| **L3 调度** | 当 L3 需要协同时，发布任务、选择节点、分配子任务 |
| **可选：本地模型** | 高级能力，L2 节点可挂载本地模型，为 L3 提供额外算力 |

### 2.2 部署形态

| 形态 | 说明 |
|------|------|
| **单机** | 一台 L2 节点，负责权限、记忆、梦境、调度 |
| **多节点集群** | 多台 L2 组成统一层，每节点可有自己的 Agent 协调工作，对外呈现为「统一 L2」 |
| **与 L3 同机** | **同一台机器可同时部署 L2 和 L3**，L2 与 L3 进程并存，通过 localhost 或 IPC 通信 |

### 2.3 API Key 管理（L2 只管理，不代理请求）

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  Layer 2 的 API Key 管理职责                                                   │
│                                                                             │
│  • L2 存储、配置、下发 API Key 给 L3 节点                                      │
│  • L2 以**密文**形式下发给 L3（L3 本地存储密文）                                │
│  • L2 **不代理** L3 的推理请求 — L3 自己发送请求处理问题                        │
│  • L2 只负责：Key 的增删改、权限分配、轮换、审计                                │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.4 记忆与梦境（含 L3 同步）

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  Layer 2 记忆系统                                                            │
│                                                                             │
│  L3 本地记忆 ──定期同步──► L2 接收 ──► 短期记忆 ──► 梦境系统 ──► 长期记忆       │
│       │                        │                        │                   │
│       │                        │                        │ 聚类/去重/融合     │
│       │                        │                        ▼                   │
│       │                        │               L2 存储优化后的记忆             │
│       │                        │                        │                   │
│       │                        │                        │ 同步回 L3         │
│       │                        │                        ▼                   │
│       │                        │               L3 可删除本地，使用 L2 版本    │
│       └────────────────────────┴────────────────────────────────────────────┘
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.4.1 记忆 Namespace 隔离（细粒度权限）

L2 记忆支持 **namespace**（命名空间）实现物理隔断，杜绝数据越权穿透：

| 机制 | 说明 |
|------|------|
| **写入** | `POST /memory/sync` 请求体可声明 `namespace`（默认 `default`），记忆按 `(sub_account_id, node_id, namespace)` 存储 |
| **检索** | `GET /memory/search` 支持 `namespaces` 参数，仅在子账号 `allowed_memory_namespaces` 范围内检索 |
| **RBAC** | 子账号配置 `allowed_memory_namespaces`（如 `["customer_service_kb", "default"]`），请求的 namespace 必须在其列表中，否则 403 |
| **LanceDB** | `memories` 表含 `namespace` 列，插入与检索时作为核心过滤维度 |

**示例**：客服部子账号仅配置 `allowed_memory_namespaces: ["customer_service_kb"]`，则无法读写 `finance_dept` 等其它命名空间。

### 2.5 L2 节点与 Agent

- 每个 L2 节点可运行**协调 Agent**，负责：
  - 集群内任务协调
  - 与其他 L2 节点的通信（若为集群）
  - 与 Layer 1 的心跳、策略同步
- 协调 Agent 不执行用户任务，只做元调度与协调。

### 2.6 可选：本地模型

- L2 节点可配置本地模型（Ollama、vLLM 等）
- 当 L3 请求算力且本机 Skill 不足时，L2 可将部分推理任务路由到本地模型
- 此为**高级可选**能力，不影响核心架构

### 2.7 每节点独立配置（L2 管理）

- **API Key**：L2 为每个 L3 节点配置可用的 API Key，以**密文**形式下发给 L3
- **模型通道**：L2 为每个节点配置模型端点（如 L3-1 用 gpt-4，L3-2 用 qwen）
- **L2 不代理请求**：L3 收到密文 Key 后自行解密、自行调用外部 API

## 三、Layer 3：Jachin L3 执行面（对标 OpenClaw 类单机）

### 3.1 定位

**Jachin L3**：默认 **单主轴 `run_agent` ReAct**（可选 `delegate`/后台/`coordinate`）；多 Skill/MCP、本地记忆、任务执行、可协同。混合架构见 **[architecture/JACHIN_HYBRID_AGENT_ARCHITECTURE.md](./architecture/JACHIN_HYBRID_AGENT_ARCHITECTURE.md)**。

| 维度 | OpenClaw 单机（对标） | Jachin L3 |
|------|---------------|----------------|
| **Agent** | 单/多 Agent，按 channel 路由 | 每节点有 Agent，可分身多个 |
| **Skill** | ClawHub 10,700+ skills | MCP + SKILL.md + JPP .wasm |
| **执行** | Agent run/attempt，ReAct 循环 | 同左，ReAct + 工具调用 |
| **协同** | 无 | 通过 L2 调度，与其他 L3 协同 |
| **记忆** | 本地 MEMORY.md | 本地记忆 + 定期同步 L2，L2 梦境后回传 |
| **模型 API** | 全局配置 | 多模型 API，多 Agent 可共用（非 1:1） |
| **API Key** | 本地持有 | L3 本地持**密文 Key**，请求时解密后自行调用 API；L2 只管理 Key |

### 3.2 每个 L3 节点的结构

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  Jachin L3 节点（单主轴 ReAct；能力对标 OpenClaw 类）                          │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  主 Agent + 子 Agent 们                                               │   │
│  │  • 多 Agent 与多模型 API 匹配：非 1 Agent = 1 模型                      │   │
│  │  • 一个 API Key 可被多个 Agent 共用                                    │   │
│  │  • 本地持密文 Key，发送请求时解密为明文后自行调用外部 API               │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  Skills (已安装)                                                      │   │
│  │  • MCP 工具、SKILL.md、JPP .wasm                                      │   │
│  │  • 由主账号/子账号权限控制可安装范围                                    │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  本地记忆 (文档/JSON)                                                  │   │
│  │  • 定期同步至 L2，L2 梦境优化后回传                                     │   │
│  │  • 同步后可删除本地，或保留缓存                                         │   │
│  │  • 可选：Redis 共享（性能/系统允许时）                                  │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  本地密文 Key（由 L2 下发）                                           │   │
│  │  • 发送请求时解密为明文，自行调用外部 API                              │   │
│  │  • L2 只管理 Key，不代理请求                                          │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  部署：可与 L2 同机                                                    │   │
│  └─────────────────────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.3 Agent 与模型 API 的匹配关系

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  L3 节点内：多 Agent、多模型 API                                              │
│                                                                             │
│  模型 API（Key 由 L2 管理、以密文下发，L3 本地持密文）：                       │
│  • api-1: gpt-4o      • api-2: qwen-max      • api-3: ollama/local          │
│                                                                             │
│  Agent 与 API 的匹配（非 1:1）：                                              │
│  • Agent A 可选用 api-1 或 api-2                                             │
│  • Agent B 可选用 api-1（与 A 共用）                                          │
│  • Agent C 可选用 api-3                                                      │
│  • 一个 API Key 可被多个 Agent 共用，无需「一个 Agent 绑定一个模型」          │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.4 Agent 分身

- **分身**：主 Agent 根据任务复杂度或 Skill 需求，动态创建子 Agent
- **子 Agent 属性**：
  - 独立的 System Prompt（如「你是资深程序员」）
  - 独立的工具集（如仅代码相关 Skill）
  - 独立的会话上下文
- **生命周期**：任务完成后子 Agent 可销毁，或保留供后续复用

### 3.5 L3 本地记忆与同步

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  L3 本地记忆 ──► 定期同步 ──► L2 ──► 梦境优化 ──► 存储 ──► 同步回 L3          │
│                                                                             │
│  • 存储形式：文档（如 .md）或 JSON                                            │
│  • 同步周期：可配置（如每小时、每 6 小时）                                     │
│  • L2 梦境后：聚类、去重、融合，存储优化后的记忆                               │
│  • 回传 L3：L3 可删除本地文档/JSON，仅保留 L2 返回的版本                       │
│  • 可选：部分节点在性能/系统允许时使用 Redis 共享数据，减少同步开销             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.6 L3 的 Ingress（入口）

- L3 节点可包含**多种入口**，与 OpenClaw 的 Channels 对标：
  - **Tauri 桌面端**：UI、HITL 弹窗、语音唤醒
  - **IM 渠道**：Telegram、飞书等（通过 Layer 1 Webhook 或直连）
  - **CLI**：jachin-cli shell
  - **Web 控制台**：内嵌或独立
- 所有入口归一化为「任务」注入 L3 的 Agent，由 Agent + Skills 执行

### 3.7 与 L2 同机部署

- **同一台机器可同时运行 L2 和 L3 进程**
- 通信：localhost 或 IPC，低延迟
- 适用：个人开发、小型部署、家庭单机

### 3.8 L3 与 OpenClaw 的等价关系

| OpenClaw 组件 | Jachin V2 L3 对应 |
|---------------|-------------------|
| Gateway（入口 + 路由） | L3 的 Ingress（Tauri/IM/CLI） |
| Agent Runtime | L3 的 Agent + 分身 |
| Channels | L3 的 IM/Web/CLI 入口 |
| Skills / Plugins | L3 的 MCP + SKILL + JPP |
| 单机执行 | L3 本机执行 |
| 无协同 | L3 通过 L2 协同多节点 |

## 四、任务流：单机 vs 协同

### 4.1 单机满足

```
L3-1 收到任务
     │
     ▼
本机 Skill 能否满足？
     │ 是
     ▼
本机 Agent（或分身）执行
     │
     ▼
返回结果
```

### 4.2 需要协同

```
L3-1 收到任务
     │
     ▼
本机 Skill 不能满足
     │
     ▼
向 L2 请求协同
     │
     ▼
L2 根据子账号权限筛选可用 L3 节点
     │
     ▼
L2 根据各节点实际负载分配子任务
     │
     ├──► L3-2 执行子任务 A
     ├──► L3-3 执行子任务 B
     └──► L3-4 执行子任务 C
     │
     ▼
L2 聚合结果
     │
     ▼
返回给 L3-1（发布任务的节点）
```

### 4.3 详细协同流程

```
┌──────────┐         ┌──────────────┐         ┌──────────┐
│  L3-1    │         │  Layer 2     │         │ L3-2,3,4 │
│ (发布方) │         │  (调度)      │         │ (执行方) │
└────┬─────┘         └──────┬───────┘         └────┬─────┘
     │                      │                      │
     │ 1. 请求协同           │                      │
     │ task + 所需 skill     │                      │
     │ ───────────────────► │                      │
     │                      │                      │
     │                      │ 2. 查子账号权限       │
     │                      │    可用 L3 节点       │
     │                      │                      │
     │                      │ 3. 查各节点负载       │
     │                      │    空闲/忙碌          │
     │                      │                      │
     │                      │ 4. 拆分子任务         │
     │                      │    分配策略           │
     │                      │                      │
     │                      │ 5. 下发子任务        │
     │                      │ ───────────────────► │
     │                      │                      │
     │                      │ 6. 收集结果          │
     │                      │ ◄───────────────────  │
     │                      │                      │
     │ 7. 聚合返回           │                      │
     │ ◄─────────────────── │                      │
     │                      │                      │
```

### 4.3.1 子任务状态流转

| 状态 | 说明 |
|------|------|
| **pending** | 子任务已创建、待 L3 拉取 |
| **in_progress** | L3 已从队列取到任务，正在执行（取到即标记，避免重复下发） |
| **done** | L3 已提交结果，L2 聚合完成 |

**流程**：L2 创建子任务 → 推入 Redis 队列 `l3_task_queue:{node_id}` → L3 通过 `GET /coordinate/poll` RPOP 取任务 → 取到后 DB 标记 `in_progress` → L3 执行完毕 `POST /coordinate/result` → DB 标记 `done` → 当该主任务下所有子任务均为 `done` 时，L2 聚合结果并更新主任务状态。

### 4.4 子任务分配策略

| 策略 | 说明 |
|------|------|
| **负载均衡** | 选当前最空闲的 L3 节点 |
| **Skill 匹配** | 选已安装所需 Skill 的节点 |
| **亲和性** | 优先选与发布方同局域网的节点（低延迟） |
| **能力标签** | 根据节点声明的能力（GPU、内存等）分配重型任务 |

## 五、L2 集群与统一层

### 5.1 多节点 L2

- L2 可以是多台机器组成的集群
- 对外呈现为**统一 Layer 2**，内部通过协调 Agent 或网关通信
- 记忆可集中存储（如共享 DB）或分片存储

### 5.2 L2 无状态集群（Stateless）

为实现 Kubernetes 横向扩缩容，L2 支持**无状态化**改造：

| 组件 | 实现方式 |
|------|----------|
| **L3 在线状态** | 迁移至 Redis `l3_node_status:{node_id}`，TTL 60 秒；L3 调用 `poll` 或心跳时写入 |
| **协同任务队列** | 迁移至 Redis `l3_task_queue:{node_id}`；子任务创建时 LPUSH，L3 poll 时 RPOP |
| **调度器** | 从 Redis 读取全网存活 L3 节点列表，进行能力匹配与打分 |
| **L1 心跳** | 仅 Leader 执行（Redis 锁 `l2_cluster_leader_lock` 选举） |

**效果**：任意 L2 节点均可处理任意 L3 的请求；L3 连接到 L2 节点 A 拉取任务，任务可能由节点 B 创建并推入 Redis，节点 A 直接 RPOP 即可返回。Redis 不可用时自动回退 SQLite/本地逻辑（单节点模式）。

### 5.3 每 L2 节点的 Agent

- 每个 L2 节点可有**协调 Agent**
- 职责：
  - 接收 L3 的协同请求
  - 与其他 L2 节点协商（若任务跨节点）
  - 与 Layer 1 同步策略、上报状态
- 协调 Agent 不执行用户级 ReAct，只做元操作

### 5.4 统一层入口

- 类似 L2 Gateway 设计：L3 只连统一入口（网关或主节点）
- 网关负责：认证、路由、任务分发、结果聚合
- **部署示例**：`docker-compose.l2-cluster.yml` 启动 3 个 L2 实例 + Nginx，单一入口 18888 端口，`least_conn` 负载均衡

## 七、数据流与协议

### 7.1 L3 → L2 请求类型

| 类型 | 说明 | 协议 |
|------|------|------|
| **Key 获取** | L3 向 L2 获取密文 Key（L2 只管理，不下发明文） | `GET /keys`（返回密文） |
| **记忆检索** | L3 向 L2 查询记忆（支持 `namespaces` 参数，按 allowed_memory_namespaces 过滤） | `GET /memory/search?q=...&namespaces=...` |
| **记忆同步** | L3 将本地记忆（文档/JSON）同步至 L2（请求体可声明 `namespace`，默认 `default`） | `POST /memory/sync` |
| **协同请求** | L3 请求 L2 调度多节点 | `POST /coordinate/task` |
| **权限校验** | L3 执行前校验子账号权限 | `POST /auth/check` |
| **策略同步** | L2 从 L1 拉取策略，下发给 L3 | 心跳 + 推送 |

**注**：L3 的推理请求**不经过 L2**，L3 持密文 Key，解密后自行调用外部 API。

### 7.2 L2 → L3 下发

| 类型 | 说明 |
|------|------|
| **密文 Key** | L2 下发给 L3 的 API Key（密文形式） |
| **子任务** | 协同时，L2 向选中 L3 下发子任务 |
| **策略更新** | 权限、Skill 白名单等变更 |
| **记忆回传** | 梦境优化后的记忆，同步回 L3（L3 可删本地） |

### 7.3 子任务协议

```json
{
  "task_id": "uuid",
  "parent_task_id": "uuid",
  "parent_l3_node_id": "xxx",
  "sub_account_id": "xxx",
  "payload": {
    "intent": "处理第 3 段 PDF",
    "skill_required": "pdf_parser",
    "input_data": "..."
  },
  "timeout_seconds": 60
}
```

**P1+（多节点原生派发）**：当 `input_data` 为 JSON 且包含 `"type": "native_tool"` 时，执行节点 **直接 `run_tool`**，不再对该子任务启动子 Agent LLM。示例：

```json
{
  "type": "native_tool",
  "tool_id": "core:shell_exec",
  "action_input": { "command": "git status", "timeout": 60 }
}
```

开关：`~/.jachin/nexus_config.json` → `intelligence_p1.coordinate_native_tool_dispatch`（默认启用）。详见 [INTELLIGENCE_UPGRADE_OVERVIEW.md](./INTELLIGENCE_UPGRADE_OVERVIEW.md) §二。

## 八、配置与部署

### 8.1 每节点配置矩阵

| 节点类型 | API Key | 模型通道 | 记忆 | 权限 |
|----------|---------|----------|------|------|
| **L1** | 不涉及 | 不涉及 | 不涉及 | 平台主账号 / 用户主账号 |
| **L2 节点** | L2 持有并管理，以密文下发 L3 | L2 配置每节点通道 | 本节点或共享 | 校验子账号 |
| **L3 节点** | 本地持**密文**，请求时解密后自行调用 | 由 L2 分配，L3 持密文 Key | 本地 + L2 同步 | 受子账号约束 |

### 8.2 API Key 与 L3 的使用方式

- **原则**：L2 只管理 Key，不代理 L3 的推理请求
- **流程**：L2 以**密文**形式下发给 L3 → L3 本地存储密文 → L3 发送请求时**解密为明文** → L3 **自行**调用外部 API
- **禁止**：L3 本地**明文**存储 API Key；仅允许密文存储，使用时解密

### 8.3 同机部署

- **L2 + L3 同机**：同一台机器可同时运行 L2 和 L3 进程，通过 localhost 通信

## 十、总结

### 10.1 新架构核心

1. **L1**：平台，注册/管理若干用户主账号；平台主账号管平台内部，与 L2/L3 无关
2. **L2**：子账号在 L2 创建，权限、记忆、梦境、L3 调度、**API Key 管理**（密文下发，不代理请求），可单机可集群，可与 L3 同机
3. **L3**：单体 = OpenClaw，本地持**密文 Key**，请求时解密后自行调用 API，L2 只管理 Key

### 10.2 与 OpenClaw 的关系

- **L3 单体**：功能对标 OpenClaw，可独立运行、安装 Skills、执行任务
- **超越 OpenClaw**：通过 L2 获得集中记忆、梦境优化、多 L3 协同、主/子账号权限

### 10.3 划时代意义

- **执行平面下沉**：从 L2 下沉到 L3，L3 成为真正的「工作节点」
- **控制平面上浮**：L2 专注权限、记忆、调度，不做用户级推理
- **权限细粒度**：主/子账号，控制 L3 节点、内容、Skill、模型
- **协同原生**：单节点不足时，L2 调度多 L3，透明协同

## 十一、逐步详解：关键流程

### 11.1 步骤一：用户主账号注册与子账号创建

```
1. 用户在 Layer 1（平台）注册/登录
   → 获得用户主账号 (main_user_id)
   → 每个用户主账号管理其自己的 L2 + L3 系统

2. 用户主账号登录 Layer 2 管理界面
   → 进入「子账号管理」

3. 用户主账号在 Layer 2 点击「创建子账号」
   → 输入名称、选择权限模板（或自定义）
   → 权限包括：可用的 L3 节点、L2 上可访问的记忆与资源、Skill 白名单、是否允许发布协同任务

4. Layer 2 创建 sub_account 记录
   → 关联 main_user_id（用户主账号）
   → 写入 sub_account_permissions（存于 L2）

5. 子账号在 L2 层生效
   → L2 校验请求时查 sub_account_permissions
   → 子账号根据权限管理允许的 L3 节点和 L2 部分记忆与资源
```

### 11.2 步骤二：L3 节点注册与权限绑定

```
1. L3 节点首次启动
   → 向 L2 注册（携带设备指纹、能力标签）
   → L2 分配 l3_node_id，写入 layer3_nodes 表

2. 用户主账号在 Layer 2 管理界面「设备管理」
   → 看到所有已注册的 L3 节点
   → 将 L3 节点「分配给」某子账号
   → 即：该子账号的「可用 L3 节点」列表中加入此节点

3. 子账号登录/使用时
   → 只能看到、调用被分配给他的 L3 节点
   → 只能访问权限范围内的 L2 记忆与资源
```

### 11.3 步骤三：L3 收到任务时的完整决策树

```
L3 节点收到用户任务（如「帮我分析这 100 份 PDF」）
    │
    ▼
┌─────────────────────────────────────┐
│ 1. 本机 Skill 能否满足？             │
│    检查已安装 Skill 是否覆盖任务需求  │
└─────────────────────────────────────┘
    │
    ├── 能 ──► 本机 Agent（或分身）执行
    │              │
    │              ▼
    │         返回结果，结束
    │
    └── 不能 ──► 2. 向 L2 请求协同
                      │
                      ▼
                 ┌─────────────────────────────────────┐
                 │ 3. L2 校验子账号权限                 │
                 │    当前请求是否来自有「协同权限」的子账号？│
                 │    该子账号可用的 L3 节点有哪些？     │
                 └─────────────────────────────────────┘
                      │
                      ├── 无权限 ──► 返回错误「无协同权限」
                      │
                      └── 有权限 ──► 4. L2 查询可用 L3 节点负载
                                        │
                                        ▼
                                   5. L2 拆分子任务，按策略分配
                                        │
                                        ▼
                                   6. L2 向各 L3 下发子任务
                                        │
                                        ▼
                                   7. 各 L3 执行，回传结果
                                        │
                                        ▼
                                   8. L2 聚合结果，返回给发布方 L3
```

### 11.4 步骤四：Agent 分身的具体机制

```
主 Agent 收到任务
    │
    ▼
任务解析：需要「代码编写」+「文档撰写」两个能力
    │
    ▼
主 Agent 决定分身
    │
    ├──► 创建子 Agent A
    │    • system_prompt: "你是资深程序员，只负责写代码"
    │    • tools: [code_skill, git_skill]
    │    • 执行「编写代码」子任务
    │
    └──► 创建子 Agent B
         • system_prompt: "你是技术文档工程师，只负责写文档"
         • tools: [doc_skill, markdown_skill]
         • 执行「撰写文档」子任务
    │
    ▼
主 Agent 等待子 Agent 完成，合并结果
    │
    ▼
子 Agent 可销毁，或保留供后续复用（可配置）
```

### 11.5 步骤五：L3 记忆同步流程

```
1. L3 本地记忆（文档或 JSON）定期触发同步
   → 发送至 L2 POST /memory/sync

2. L2 接收记忆，写入短期存储
   → 进入梦境流水线

3. L2 梦境系统处理
   → 聚类、去重、融合、冲突消解
   → 写入长期记忆（LanceDB 等）

4. L2 将优化后的记忆同步回 L3
   → L3 可删除本地文档/JSON，或保留缓存

5. 可选：部分 L3 节点使用 Redis 共享
   → 多节点间低延迟共享，减少同步频率
```

### 11.6 步骤六：L3 推理请求（本地密文 Key）

```
1. L3 从 L2 获取密文 Key（或已缓存）
   → 本地存储密文，不存明文

2. L3 Agent 需要调用模型
   → 从本地读取密文 Key
   → 解密为明文（仅内存中，不落盘）

3. L3 自行发送请求至外部 API（OpenAI、通义等）
   → 携带解密后的 Key，直接调用
   → 不经过 L2

4. L2 只负责 Key 的管理（存储、下发、轮换、审计）
   → 不代理、不转发 L3 的推理请求
```

### 11.7 步骤七：L2 调度时的节点选择算法

```
输入：任务 task、子账号 sub_account_id
输出：选中的 L3 节点列表 + 子任务分配

1. 查权限：sub_account 可用的 l3_node_ids
2. 过滤：排除离线、过载的节点
3. 匹配：优先选已安装所需 Skill 的节点
4. 负载：按当前队列长度、CPU/GPU 使用率排序
5. 亲和：同局域网优先（可选）
6. 分配：将子任务按策略（轮询、最少连接等）分配给选中节点
```

| **多节点** | 无 | L2 可集群，L3 可多节点 |
| **API Key** | 本地持有 | L2 管理，L3 持密文、解密后自行调用 |
| **模型配置** | 全局 | L2 管理，多 Agent 可共用多通道 |
| **HITL** | 有 | 保留 |
| **Compaction** | 有 | 保留 |
| **供应链安全** | ClawHavoc 风险 | JPP Wasm 零信任 |
| **智能化 P1/P1+** | 社区各插件自行其是 | 偏好文件 + 澄清队列 + 只读工具缓存 + shell 策略；后台 shell 与协同 `native_tool`（见 `l3_node/intelligence_p1.py` 等） |
