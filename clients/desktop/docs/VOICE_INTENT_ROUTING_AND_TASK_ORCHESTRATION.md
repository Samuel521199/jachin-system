# 语音意图识别与任务编排方案

> **状态**：设计稿（未编码）· **本项目语音模块的主方案**
> **产品目标**：做出 JARVIS 那种「多线程从容感」—— 后台在拼命干活，前台仍能随时跟你说话。
> **核心思路**：三级任务分流 + 聊天/任务双通道并行（用户说话永远不被正在执行的任务堵住）
> **第一版最重要的事（比分类准不准更重要）**：先把「聊天通道」和「任务执行通道」彻底物理隔开。分类分错了还能调规则，两个通道没隔开的话体验立刻崩掉。
> **关联文档**：`VOICE_QA_PROCESS_PIPELINE.md`、`VOICE_UNIFIED_PIPELINE_PROPOSAL.md`、`VOICE_BARGE_IN_AND_WAKE_ACK.md`、`docs/前台闲聊与后台重负荷任务的物理隔离与背压熔断.md`

## 名词速查（先看这里）

| 名词 | 是什么 |
|------|--------|
| **STT** | 语音转文字（Speech-to-Text），把用户说的话变成文字 |
| **TTS** | 文字转语音（Text-to-Speech），把 Jachin 的回复念出来 |
| **L3** | Jachin 的核心 AI 大脑，负责理解和执行任务 |
| **JVS** | Jachin Voice Service，负责麦克风采集和 STT/TTS 的语音服务 |
| **Orb** | 界面上那个发光的球形 UI，用颜色/动画表示系统状态 |
| **HUD** | 悬浮信息面板，显示进度、日志等文字信息 |
| **Dispatcher（分流器）** | 收到用户说的文字后，第一步判断这句话是闲聊、短任务还是长任务 |
| **chat\_lane（聊天通道）** | 永远保持开启的「实时对话通道」，不会被任何任务堵住 |
| **task\_lane（任务通道）** | 后台任务的专属执行通道，和聊天通道互不干扰 |
| **task\_slot（任务槽）** | 桌面侧记录一个后台任务的对象（含任务ID、名称、当前状态） |
| **voice\_session（语音会话）** | 用户唤醒 Jachin 后开启的一段对话窗口，默认 60 秒无说话则关闭监听 |
| **KWS** | 关键词检测（Keyword Spotting），监听唤醒词「嘿贾欣」 |
| **VAD** | 语音活动检测，判断麦克风里现在有没有人在说话 |
| **barge-in（打断）** | 用户在 Jachin 说话时插嘴，系统需要停止 TTS 并处理新输入 |
| **ReAct** | L3 的「思考→调工具→观察结果→再思考」循环，是执行工具任务的方式 |
| **受理轮** | L3 接到长任务时，用一个极短的「受理轮」确认任务、投递到后台，而不是立刻开始干 |
| **allowlist（白名单）** | 受理轮期间 L3 只能用的工具列表，宿主强制执行，不靠 L3 自觉 |
| **direct\_llm（直连模型）** | 闲聊时跳过工具调用，直接用大模型回答，速度最快 |
| **Worker** | 后台执行任务的工作进程 |
| **zombie\_tasks（僵尸任务）** | 上次 App 关闭时没跑完、遗留下来的后台任务 |
| **VAD 避让** | 检测到用户在说话时，延迟 TTS 播报，不和用户抢话 |

## 0. 这份方案是什么、为什么这么做

### 0.1 四个核心支撑点（必须守住）

| 支撑点 | 具体含义 |
|--------|----------|
| **三条体验轨道** | 闲聊 / 短任务 / 长任务 —— 足够简单，V1 先做这三条 |
| **长任务扔后台就释放聊天通道** | 用户说「把 50 个 PDF 都摘要一遍」，语音入口不能卡在那等 AI 做完，**应该立刻能继续说话** |
| **延迟掩盖不是装饰** | 本地播一声「收到」、Orb 变色、HUD 显示进度，这些是在告诉用户「我还在听，也在办」，没有这些用户会以为死机了 |
| **插嘴要先判断再处理** | 任务没做完时用户继续讲话，不能一律打断（用户可能只是想聊天），也不能一律并行（可能是要修改任务） |

### 0.2 系统整体流程图

```text
用户说话 → STT 转成文字
      │
      ▼
┌─────────────────────────────────────┐
│  ① 分流器（Dispatcher）              │
│    判断：闲聊？短任务？长任务？模糊？  │
│    必须在「真正发给 L3」之前完成      │
└──────────────┬──────────────────────┘
               │
   闲聊         │   短任务（≤5s）        长任务（可能要几分钟）
   直接快速回答  │   前台执行              受理后扔后台
               │                        → 聊天通道立刻释放
               ▼
┌──────────────────────────────────────┐
│  ② 即时反馈（Latency Masking）         │
│    判断完就立刻播音/变色，不等 L3      │
└──────────────┬───────────────────────┘
               ▼
┌──────────────────────────────────────┐
│  ③ 插嘴仲裁（Interruption Router）    │
│    任务跑着时用户继续说话该怎么办      │
│    终止 / 修改 / 并行 / 问进度        │
└──────────────────────────────────────┘
```

## 1. 现在有什么问题

### 1.1 现状的错误

目前语音链路接收到 STT 文字之后，**几乎所有情况都走同一条路**：直接调 `doActualSend`，启动 TTS 会话，进入「思考中」状态，把请求发给 L3。

问题在于：**如果要判断「这是短任务还是长任务」，但判断逻辑放在这步之后** —— 长任务仍然会先占住前台，只是晚一点才被 L3 的 prompt 建议扔到后台，**用户体验已经被破坏了**。

### 1.2 用户感受 → 根本原因

| 用户感受 | 根本原因 |
|----------|----------|
| 说个「你好」也要等半天，还听到工具执行日志 | 没有走闲聊快轨 |
| 让处理 50 个 PDF，界面卡死 | 聊天/任务没物理隔开；分流器插入时机太晚 |
| 任务在跑的时候插不了嘴、问不了进度 | 缺少插嘴仲裁机制 + 任务 ID 绑定 |
| 觉得「死机了」 | 没有即时反馈；HUD 只有「心跳」指示器，没有真实进度 |
| 说了句话系统没反应 | 模糊意图没有定义处理流程 |
| 重新唤醒后不知道之前任务怎样了 | 会话恢复机制和语音层没打通 |

## 2. 设计目标与边界

### 2.1 要做什么（按优先级）

1. **P0 物理隔开**：聊天通道永远不被长任务堵死（分流器位置正确 + 受理轮白名单强制执行）
2. **P1 三级分流**：分流器 + 稳定的 `DispatcherDecision` 数据结构
3. **P2 连接感**：任务确认音、Orb 状态变化、HUD 结构化进度
4. **P3 插嘴仲裁**：终止 / 修改 / 并行 / 查进度 + 任务 ID 精确绑定
5. **P4 会话韧性**：模糊意图澄清、会话到期、跨会话任务恢复
6. **P5 分类精度**：先用关键词规则，可选 AI 辅助分类；不先追求高精度

### 2.2 不做什么

- 在 JVS / Rust 层运行 LLM（太重）
- 声纹识别（单独课题）
- 保证后台线程 100ms 内强制停止
- 任务「热修改」（V1 用取消+重提交代替）

## 3. 代码插入位置（实施时必看）

### 3.1 现在的（错误的）路径

```text
STT → onCompanionInject(text) 或 voiceCore
        → doActualSend(t)          ← 立刻启动 TTS 会话
        → 状态变为「思考中」        ← 立刻占住前台
        → 通过 Sensory WS 发给 L3  ← 长任务也要等 L3 完整走完才能扔后台
```

**关键代码位置（桌面端）**：`chat.tsx` 里的 `doActualSend`、`onCompanionInject`；`voice/voiceOrchestrator.ts` 里的 `startSession`。

### 3.2 目标路径（改完后的样子）

```text
STT → utteranceReady(text, sessionId)
        → dispatchUtterance(text)     ← 新增的统一入口，所有 STT 结果都走这里
              ├─ 分流器判断类型 → DispatcherDecision
              ├─ [短任务/长任务] 立刻播任务确认音 + Orb 变色
              ├─ [长任务] 在本地创建一个 task_slot 记录
              ├─ [有正在进行的任务] 先走插嘴仲裁
              ├─ [模糊意图] 进入澄清等待状态（见附录 A）
              └─ routeToL3(decision)  ← 只有这个函数可以调用 doActualSend
                    ├─ 闲聊 → 直连大模型（不走工具）
                    ├─ 短任务 → 前台执行（有时间限制 + 超时自动升级）
                    └─ 长任务 → 只做受理（白名单限制，不能乱用工具）
        → TTS 播报器只在「需要念出来的情况」才启动
```

### 3.3 实施时的硬性规则

| 规则 | 原因 |
|------|------|
| **禁止** STT 回调直接调 `doActualSend` | 必须全部经过 `dispatchUtterance` |
| 长任务**禁止**在分流判断完成前把状态切到「思考中」 | 应该先播任务确认音 + Orb 变成「工作中」态 |
| `doActualSend` 必须带上完整的 voice envelope（含分流结果快照） | L3 读这个结构体来决定行为，不靠 prompt 里写的建议 |
| 意图模糊时**不得**直接调 `routeToL3` | 先 TTS 问用户，进入澄清等待状态 |

## 4. 分流器输出的数据结构（稳定规范）

分流器每次判断的结果必须输出一个 **`DispatcherDecision`** 对象（版本化 JSON）。桌面端和 L3 共用同一份，**禁止**两端各自解析一套不同的字段。

### 4.1 完整示例

```json
{
  "schema_version": 1,
  "decision_id": "dec-uuid",
  "utterance_id": "ut-uuid",
  "voice_session_id": "vs-uuid",
  "generation": 3,

  "tier": "CHIT_CHAT",
  "intent_class": "CHITCHAT",
  "confidence": 0.92,
  "interrupt_verdict": "NONE",
  "task_title": "批量摘要 PDF",
  "target_task_id": null,
  "execution_lane": "direct_llm",
  "route_source": "rule",

  "active_task_ids": ["bg-abc"],
  "task_context_summary": "PDF 摘要任务：50份，已处理 12/50",

  "latency_masking": {
    "play_task_ack": false,
    "orb_mode": "listening",
    "hud_terminal": false
  },
  "router_hints": {
    "force_background": false,
    "prefer_direct_llm": true,
    "acceptance_round": false,
    "max_foreground_tool_sec": 5,
    "inject_task_context": false,
    "clarification_handle": "",
    "awaiting_confirmation": false
  }
}
```

### 4.2 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `schema_version` | 数字 | ✅ | 当前版本 `1`，有破坏性改动时 +1 |
| `tier` | 枚举 | ✅ | 三个轨道：`CHIT_CHAT`（闲聊）/ `SHORT_TASK`（短任务）/ `LONG_TASK`（长任务） |
| `intent_class` | 枚举 | ✅ | 细分意图类型，见下表 |
| `confidence` | 小数 | ✅ | 分流器的把握程度，0.0～1.0 |
| `interrupt_verdict` | 枚举 | ✅ | 插嘴类型：`NONE`（不是插嘴）/ `STATUS`（问进度）/ `ABORT`（终止）/ `MODIFY`（修改）/ `PARALLEL`（继续聊）/ `NEW_TASK`（新建任务）/ `RESUME`（继续被暂停的任务） |
| `task_title` | 字符串 | 可选 | 新建任务时用的人话名称，方便 HUD 展示和口头指代 |
| `target_task_id` | 字符串或null | 可选 | 插嘴/控制指令要操作的具体任务 ID，见 §4.4 |
| `execution_lane` | 枚举 | ✅ | 走哪条执行路径，见下表 |
| `route_source` | 枚举 | ✅ | 分流来源：`rule`（关键词规则）/ `lite_model`（小模型判断）/ `l3_gateway`（L3 判断） |
| `active_task_ids` | 数组 | 可选 | 当前语音会话里有哪些正在跑的后台任务 |
| `task_context_summary` | 字符串 | 可选 | 闲聊时注入给 L3 的后台任务简况（最多 50 字），让 L3 回答时可以顺带提一下任务进度 |
| `latency_masking` | 对象 | ✅ | 即时反馈配置，桌面消费，L3 可忽略 |
| `router_hints.inject_task_context` | 布尔 | 可选 | `true` 时 L3 的 system prompt 里追加任务简况 |
| `router_hints.clarification_handle` | 字符串 | 可选 | 正在等用户回答的那个澄清问句的标识，续答时带回来 |
| `router_hints.awaiting_confirmation` | 布尔 | 可选 | `true` 表示现在在等用户确认「要不要并行跑新任务」 |

**`intent_class` 细分含义**

| 值 | 含义 |
|----|------|
| `CHITCHAT` | 闲聊，没有具体任务 |
| `QUERY_LIGHT` | 轻量查询（天气、时间等，几乎不需要工具） |
| `TASK_SYNC` | 短时间内能完成的同步任务 |
| `TASK_ASYNC` | 需要后台长时间跑的异步任务 |
| `CONTROL` | 控制指令（停止、继续、查进度等） |
| `CLARIFY_REPLY` | 用户在回答系统刚才的澄清问句 |
| `AMBIGUOUS` | 意图模糊，系统判断不了，需要问用户 |

**`execution_lane` 执行路径含义**

| 值 | 含义 |
|----|------|
| `direct_llm` | 直连大模型快速回答，不走工具（闲聊用） |
| `foreground` | 前台走完整工具执行流程（短任务用） |
| `background_submit` | 受理轮：确认任务后提交后台执行（长任务用） |
| `background_control` | 只用来查进度或取消任务，不新建执行流程 |
| `control_local` | 纯桌面端操作，不发给 L3（比如停止 TTS） |

### 4.3 三条轨道的核心参数对照

| 轨道 | 典型耗时 | 执行路径 | 播任务确认音？ | 注入后台任务上下文？ |
|------|----------|----------|--------------|---------------------|
| 闲聊 CHIT_CHAT | 即时～2s | `direct_llm` | 否 | **是**（若有正在跑的任务） |
| 短任务 SHORT_TASK | 2～5s | `foreground` | 是 | 否 |
| 长任务 LONG_TASK | >5s ～ 分钟级 | `background_submit` | 是 + HUD 进度 | 否 |

### 4.4 多任务时如何确认操作的是哪个任务

当后台同时跑着多个任务时，用户说「停一下」「改成 Word」，**必须确认操作的是哪个具体任务**，不能乱停：

```text
确认逻辑（按顺序尝试）：
1. 用户说的话里包含某个任务的名字关键词 → 匹配对应任务
2. 当前只有一个任务在跑 → 默认操作那个
3. 有多个任务在跑，说的话里没有明确指向 → 用小模型推断；
   还是不确定 → 意图标记为 AMBIGUOUS，TTS 问：「你是要停 PDF 摘要，还是简历分析？」
4. 最近被用户提到/关注过的任务优先（tie-break）
```

**硬性规定**：没有确认 `target_task_id` 时，**禁止对多个任务批量终止**。

## 5. 分流规则：第一层关键词过滤

这一层在 **10 毫秒内**完成判断，不调用任何 AI 模型，纯靠关键词规则。

**绝对不能只用「句子短 = 闲聊」这种规则**，「停」「取消」这样的控制词句子很短但优先级最高。

### 5.1 规则优先级表

| 优先级 | 类别 | 触发词示例 | 判断结果 | 插嘴类型 |
|--------|------|----------|----------|----------|
| P0 | **停止控制** | 停、取消、别弄了、算了、不要了、暂停 | CONTROL | ABORT（终止任务） |
| P0 | **恢复控制** | 继续、接着做、没事继续吧 | CONTROL | RESUME（恢复任务） |
| P0 | **查进度** | 进度、好了吗、怎么样了、做到哪了 | CONTROL | STATUS（查状态） |
| P0 | **停止念** | 别念了、停、闭嘴 | CONTROL | control_local（停 TTS，不停任务） |
| P1 | **确认回答** | 对、没错、就这样、好的、嗯、是的 | CLARIFY_REPLY | NONE |
| P1 | **补充修改** | 加上…、再加一个…、其实还要… | CONTROL | MODIFY（修改任务） |
| P1 | **明确短任务** | 天气、气温、几点、提醒、闹钟、打开 | SHORT/QUERY_LIGHT | NONE |
| P1 | **明确短任务** | 搜索、读文件、总结这一份、帮我查一下 | SHORT/TASK_SYNC | NONE |
| P2 | **明确长任务** | 全部、批量、所有文件、每个、整文件夹 | LONG/TASK_ASYNC | NONE |
| P2 | **明确长任务** | 生成报告、分析这些简历、爬取、导出 | LONG/TASK_ASYNC | NONE |
| P3 | **纯闲聊** | 你好、在吗、讲个笑话、陪我聊、心情怎么样 | CHIT_CHAT | NONE |
| P4 | **规则没命中** | — | — | 交给第二层 AI 判断，或兜底为查进度 |

> **三条补充说明**：
> - P0「停」：如果当前只有 TTS 在播、没有后台任务，执行停播（`control_local`），而不是终止任务。
> - P1「确认类」：只有在系统刚才问了澄清问句（`awaiting_confirmation=true` 或 `clarification_handle` 非空）的情况下，「对/好的/嗯」才会被识别为 CLARIFY_REPLY；否则当作新话题处理。
> - P1「补充类」：「加上…/其实还要…」有正在跑的任务时 → MODIFY；没有任务时 → AMBIGUOUS（意图不明确）。

### 5.2 第二层 / 第三层（可选，后续版本）

| 层 | 何时触发 | 输出 |
|----|----------|------|
| **第二层：小 AI 模型** | P4 没命中、长任务表述模糊、多任务时不知道操作哪个 | 完整的 `DispatcherDecision` JSON |
| **第三层：L3 判断** | 置信度 <0.7，或涉及 HR/PMO 等专业业务域 | `route_source=l3_gateway` |

**优化原则**：第一层规则 P0～P3 命中时，**不调**小 AI 模型，直接路由，节省延迟。

## 6. 路由逻辑与长任务受理

### 6.1 完整路由流程

```text
dispatchUtterance(text) 收到 STT 文字
  │
  ├─ 有正在跑的任务，且这句话是插嘴性质（interrupt_verdict ≠ NONE）
  │     → 走插嘴仲裁（§9）→ 按裁决结果执行（查进度/终止/并行等）
  │
  ├─ 意图模糊（AMBIGUOUS）→ 不发给 L3，进入澄清等待状态（见附录 A）
  ├─ 用户在回答澄清问句（CLARIFY_REPLY）→ 带上澄清上下文续答（见附录 A.3）
  ├─ 闲聊 → 直连大模型（顺便注入后台任务简况）
  ├─ 短任务 → 即时反馈 → 前台执行（5s 预算，超时自动升级为长任务，见 §6.4）
  └─ 长任务 → 即时反馈 → 创建任务槽 → 受理轮 → 聊天通道立刻释放
```

### 6.2 长任务受理轮：必须强制执行，不是靠 L3 自觉

当分流结果是长任务时，L3 在这一轮**只允许做一件事：确认任务、提交后台**。不允许在受理轮里去「先读几个文件看看」之类的探索行为。

**为什么要强制执行？** 如果只是在 prompt 里建议 L3「你应该先提交任务」，L3 还是可能先用工具探索一圈。宿主必须在系统层面限制它的工具调用权限。

| 受理轮允许做 | 受理轮禁止做 |
|------------|------------|
| 确认任务信息（直接返回受理话术，不用工具） | 读文件 / 执行命令 / 任何 MCP 工具 |
| 调用 `core:submit_background_task` 提交任务 | 前台多轮工具执行 |
| 调用 `core:check_background_task` 查询已有任务 | 子 Agent / 任务编排 |
| 返回受理话术（Final Answer） | 「先看一下文件结构」类探索 |

**技术要求（L3 侧）**：
- 通过 `_allowed_skills_override` 或工具过滤器在代码层强制执行，违规调用直接拒绝。
- 受理轮最多循环 3 次（`max_iterations ≤ 3`）。
- 受理轮必须在 **15 秒内**产出回复；超时则桌面播「我在处理，稍候通知你」，继续等待提交事件。

### 6.3 长任务受理后的时间线

| 时刻 | 聊天通道 | 任务通道 |
|------|----------|----------|
| 判断为长任务后 | ✅ 立刻可以说话 | 创建本地任务槽，状态=PENDING |
| L3 提交成功，返回 task_id | ✅ | 任务槽状态=RUNNING_BG（后台运行中） |
| L3 受理话术 TTS 播完 | ✅ | 后台 Worker 独立运行，互不干扰 |

### 6.4 短任务超时后自动升级为长任务

> **场景**：用户说「读一下这个文件」，被判断为短任务，但文件特别大，5 秒内 L3 没做完。这时不能静默等待，需要有明确的「接力」流程。

```text
① 分流器判断为短任务 → 前台执行，启动 5 秒计时器
② 如果 5 秒内 L3 返回了结果 → 正常播报，完成
③ 如果 5 秒超时（L3 还在执行工具）：
     桌面做以下操作：
       a. 刷新 generation（丢弃后续旧的响应分块，防止混乱）
       b. Orb 从「思考中（紫快）」变为「工作中（紫慢）」
       c. 立刻播预录的升级提示 WAV：「这个要久一点，我改成后台，完成了叫你。」
       d. 向 L3 注入一条强制指令（Observation）：
            「[VOICE_ESCALATE] 语音预算超时，请立即调用 core:submit_background_task
              提交当前任务并返回受理话术，不得继续前台工具。」
④ L3 收到 VOICE_ESCALATE → 调用提交工具 → 返回受理话术
⑤ 聊天通道立刻可用
```

**注意**：
- 升级提示音是**预录 WAV**，不等 L3 生成，立刻播。
- L3 收到 VOICE_ESCALATE 后必须在 **1 次循环内**完成提交；否则桌面强制中断前台执行。
- 升级后的任务和一开始就是长任务的完全等同，同样支持查进度、终止等操作。

## 7. 任务管理：两条通道如何并行

### 7.1 核心对象说明

| 对象 | 说明 |
|------|------|
| `voice_session`（语音会话） | 用户唤醒后的对话窗口，记录会话 ID、到期时间、generation 版本号 |
| `chat_lane`（聊天通道） | **永远开启**，处理 STT 输入、闲聊回答、插嘴 |
| `task_slot`（任务槽） | 记录一个后台任务的对象：任务 ID、名称、状态、最近被关注时间 |
| `foreground_turn`（前台占用） | 最多同时 1 个；短任务执行时占用；长任务受理轮不算「长时间占用」 |

**并发上限**：后台 Worker 数量 ≤ L3 配置的 `max_concurrent`（默认 3 个）；TTS 和麦克风各只有 1 个。

### 7.2 任务槽的状态流转

```text
PENDING（待提交）
    │  提交成功
    ▼
RUNNING_BG（后台运行中） ─────────────────────────────┐
    │                                                  │
    ├─ 收到 completed 事件  → DONE（完成）              │ 用户说「取消」
    ├─ 收到 failed 事件     → FAILED（失败）            ▼
    ├─ 收到 partial 事件    → PARTIAL（部分完成，等用户确认）   CANCELLED（已取消）
    └─ 收到 cancel_requested → CANCELLING → CANCELLED
```

- `FAILED` / `PARTIAL` 时：HUD 显示执行摘要；TTS 诚实告知；**不自动终止任务**，等用户决定。
- `DONE` 后任务槽**在内存保留 5 分钟**，期间用户还可以问「刚才那个怎么样了」。

### 7.3 语音会话到期后任务怎么办

```text
唤醒 → 创建语音会话（60 秒后到期）
  每次用户说话 → 重新计时（续期）
  Jachin 在说话（TTS 播放中）→ 不续期（防止 TTS 把会话撑着不结束）

60 秒静默，会话到期：
  ├─ 没有后台任务 → 正常关闭，Orb 变 idle（静息）
  └─ 有正在跑的任务 → 【任务不停止】，只关闭「主动监听」
       → Orb 保持「工作中（紫慢呼吸）」表示后台还在跑
       → KWS 唤醒词检测恢复（用户说「嘿贾欣」还能唤醒）
       → 再次唤醒时：检测到任务槽存在 → 自动播报状态：
            「之前的 PDF 摘要还在跑，目前 30/50。」
```

**核心保证：语音会话到期不等于任务取消。** 会话到期只是「Jachin 不再主动监听了」，任务在后台继续跑。

### 7.4 App 重启后未完成任务的恢复（晨会接力）

对接 L3 现有的「未完成任务晨会」机制，延伸到语音层：

```text
场景：用户关闭 App 后重新打开，或隔夜再次唤醒
  → 语音会话启动时，检查 zombie_tasks.json（未完成任务记录）和 RUNNING_BG 状态的任务槽
       ├─ 没有遗留任务 → 正常进入 idle
       └─ 有遗留任务 → 播报（最多 2 句话）：
               「昨天的 PDF 摘要任务还在跑，要继续还是取消？」
               → Orb 变「工作中」，等用户回答
               → 用户说「继续」→ 查询/继续任务
               → 用户说「取消」→ 走终止流程
               → 用户 10 秒没回答 → 任务自动继续，Orb 慢呼吸，不再提了
```

**不打扰原则**：晨会提示最多播 **1 次**；10 秒无响应自动跳过，任务后台继续，不强迫用户决策。

## 8. 即时反馈 & HUD 进度展示

> **为什么要「即时反馈」？** AI 模型处理请求需要时间，如果用户说完话之后什么反应都没有，感觉像死机了。即时反馈的作用是：**在 L3 还没有给出回复之前，桌面端先做出响应，让用户知道「系统收到了，正在处理」**。

### 8.1 任务确认音（300ms 内响应）

| 配置项 | 规范 |
|--------|------|
| 触发条件 | `play_task_ack=true`（短任务和长任务都触发） |
| 响应时机 | 分流判断完成后 **≤300ms**，比发给 L3 还要早 |
| 实现方式 | 本地 WAV 音频文件池（复用唤醒确认音的基础设施） |
| 文案池 | 随机选：「收到，这就去办。」/ 「正在为您处理。」/ 「交给我吧。」/ 「好，马上。」 |
| 与 L3 受理话术的衔接 | 任务确认音播完后，L3 的受理话术 TTS 紧接；如果时间上重叠，L3 的 TTS 延迟 0.5 秒渐入 |

### 8.2 Orb 状态一览

| 状态 | 颜色/动效 | 触发场景 |
|------|-----------|----------|
| listening（监听中） | 绿色快呼吸 | 用户正在说话 |
| thinking（思考中） | 紫色快旋转 | 短任务前台工具执行中 |
| **working（工作中）** | 紫色慢呼吸 + 外轨慢旋 | 长任务已提交后台，聊天已释放；或会话到期但任务仍在跑 |
| speaking（说话中） | 黄色脉冲 | TTS 播放中；此时 barge-in 仍在监听 |
| **clarifying（澄清中）** | 青白慢闪 | 等用户回答澄清问句（见附录 A） |
| idle（待机） | 青色静呼吸 | 没有正在进行的任务 |

### 8.3 HUD 进度：展示真实数据，不造假

**现在的问题**：HUD 只显示一个「心跳」指示器，用户只知道系统还活着，但不知道进展到哪了。

**要做的改动**：给 L3 的事件总线（`l3_event_bus`）增加结构化进度事件 `event: progress`：

```json
{
  "type": "background_task",
  "event": "progress",
  "task_id": "bg-xxx",
  "stage": "scanning_files",
  "message": "已扫描 12/50 个 PDF",
  "current": 12,
  "total": 50,
  "percent": 24,
  "ts": 1710000000
}
```

| 字段 | 说明 |
|------|------|
| `stage` | 机器可读的阶段标识：`queued`（排队中）/ `started`（已开始）/ `scanning`（扫描中）/ `processing`（处理中）/ `writing`（写入中）/ `finalizing`（收尾中） |
| `message` | HUD 终端里展示给用户看的一行人话进度 |
| `current` / `total` | 可选，有的话 HUD 可以显示进度条 |
| `percent` | 可选，`current/total` 或由 Worker 直接上报 |

**两条不能做的事**：
- 没有真实事件时，**不能伪造进度日志**；降级方案是「执行中…」+ 转圈指示器。
- **不能直接抓 Python 的 stdout**（顺序乱、可能有敏感信息）。

### 8.4 闲聊回复感知后台任务（让 Jachin 更有从容感）

> **为什么要做这个？** 用户在长任务执行期间问「今天吃什么」，Jachin 如果只回「建议烤肉」感觉像没意识到后台任务一样。如果顺带说「顺便说，PDF 已经处理了 12 份了」，才有 JARVIS 那种从容感。**这不是靠 L3 猜，是桌面端显式注入的。**

```text
闲聊请求 且 有正在跑的后台任务时：
  → 生成 task_context_summary = 任务名称 + 当前进度（最多 1 句话）
  → inject_task_context = true
  → 在发给 L3 的 system prompt 里追加：
      「[当前后台任务] {task_context_summary}
        若与本次回复自然，可用一句话顺带提及（不强制）。」
```

**三条约束**：
- 不强制 L3 每次都提；只在 L3 认为「顺嘴」的时候说一句。
- `task_context_summary` 最多 50 个字，不包含工具输出等敏感内容。
- 用户**主动问进度**时仍然走 STATUS 路径（查后台任务状态），不用这个注入机制代替。

### 8.5 任务完成时的播报队列（避免打断用户）

> **背景**：任务完成时，Jachin 可能正在回答用户的另一个问题（TTS 正在播），或者用户自己正在说话。这时直接打断播报是糟糕的体验。

```text
收到 completed / failed / cancelled 事件时：
  │
  ├─ 当前没有 TTS 在播 → 立刻播完成提示（一句话）
  ├─ 当前 TTS 在播     → 加入「播报队列」，等 TTS 播完再播
  │     └─ TTS 播完后 → 播队列里的完成提示
  └─ 用户在说话（VAD 检测到）→ 推迟 2 秒再检查；
       如果用户还在说 → 改为 HUD 静默通知，不念出来
```

**优先级**（同时有多个事件时的播报顺序）：终止确认 > 失败 > 部分完成 > 正常完成
**队列上限**：最多 3 条；超出的丢弃，只在 HUD 显示，不播报。

## 9. 插嘴仲裁：任务进行中用户继续说话

### 9.1 裁决结果一览

| 裁决类型 | 含义 | 行为 | 是否需要指定任务 |
|----------|------|------|------------------|
| **ABORT（终止）** | 停掉正在跑的任务 | 发取消请求 + 口头确认 | 必须指定 |
| **MODIFY（修改）** | 修改任务参数（V1：取消重提交） | 取消旧任务，带新参数重新提交 | 必须指定 |
| **PARALLEL（并行聊天）** | 用户只是聊天，任务继续 | 走闲聊通道回答（注入任务上下文），后台任务不停 | 不需要 |
| **STATUS（查进度）** | 想知道任务做到哪了 | 查后台任务状态，不新开任务执行 | 必须指定（或默认唯一任务） |
| **NEW_TASK（新建任务）** | 后台有任务时提了另一个长任务 | 先问用户是否并行（见 §9.4） | 不需要 |
| **RESUME（恢复）** | 想继续被暂停的任务 | 仅对 PAUSED 状态有效；否则告知「已经在运行了」 | 必须指定（或默认唯一任务） |

### 9.2 如何停止后台任务（工程 API 约定）

**注意**：前台的终止接口 `run_abort` 只能停前台执行，后台任务必须有独立的取消接口。

**方案 A（推荐）**：新增 Native 工具 `core:cancel_background_task`

```json
// 调用参数
{ "task_id": "bg-xxx", "reason": "user_voice_abort" }

// 成功响应
{
  "status": "cancel_requested",
  "task_id": "bg-xxx",
  "message": "已请求停止；若已落盘部分结果将保留。"
}
```

**取消的行为语义（协作式取消，不是强杀）**：
- 任务在**排队中**（queued）：直接标为已取消，不启动 Worker。
- 任务**正在运行**（running）：设置 `cancel_requested` 标志，Worker 在下一个协作点检查并停止（走现有的 `asyncio.CancelledError` 路径）。
- **不承诺** 100ms 内停止 shell 命令或 MCP 调用；话术要诚实，说「已停止继续处理」而不是「已清除」。

**方案 B（备选）**：通过 Sensory WebSocket 发 `background_task_control` 消息，效果等价。

### 9.3 修改任务（V1 的简化方案）

V1 不做「热修改」（直接修改正在运行的任务参数），而是：**取消旧任务 + 带新参数重新提交**。热修改放 I5+ 迭代。

### 9.4 提新任务时询问是否并行

> **场景**：后台 PDF 任务还在跑，用户说「再帮我分析一下这份合同」，这是一个新的长任务。系统不能自作主张直接开，也不能拒绝，要先问。

```text
触发 NEW_TASK 裁决后：
  → TTS 问：「之前的任务还在跑，新任务要一起跑，还是等完了再说？」
  → 进入等待状态：
      awaiting_confirmation = true
      Orb 变「澄清中（青白慢闪）」
      启动 15 秒确认计时器

用户回答：
  → 「一起跑」/ 「同时」     → 并行提交新任务，两个任务槽同时存在
  → 「等完了再说」           → 新任务加入「待确认队列」，提示「到时我会提醒你」
  → 沉默 15 秒无回应         → 默认「不并行」，新任务进待确认队列
  → 「取消」/ 「算了」       → 丢弃新任务，原任务继续

待确认队列的运转：
  → 原任务完成时 → TTS 提醒：「XX 做完了，之前的 YY 要开始吗？」
  → 用户确认 → 正常提交新任务
  → 队列最多保留 2 条；超出时提示：「新任务太多，请告诉我最想做的那个」
```

## A. 附录：模糊意图的澄清流程

> 当分流器判断不了用户想说什么时（`intent_class = AMBIGUOUS`），不能乱猜，要先问清楚。

### A.1 什么时候进入澄清状态

```text
分流器输出 intent_class = AMBIGUOUS
  → 桌面进入「澄清等待状态」，不发给 L3 执行任何任务
```

### A.2 澄清过程

```text
① L3 生成一个澄清问句（极短的一次 ReAct，只输出问句，不调工具）
   → TTS 播出：「你是想处理所有文件，还是只处理这一份？」
② Orb 变「澄清中（青白慢闪）」
③ 桌面记录 clarification_handle（包含问句摘要、原始 utterance_id、超时时间）
④ 聊天通道保持开启（用户可以随时说话）
⑤ 超时时间：20 秒
```

### A.3 用户回答后的处理

```text
用户说话（clarification_handle 不为空时）：
  ├─ 如果是控制类指令（如「算了」）→ 取消澄清，Orb 回 idle
  └─ 其他回答 → 识别为 CLARIFY_REPLY
       → 发给 L3（带上 clarification_handle 作为上下文）
       → L3 把原始问题 + 用户的澄清回答合并，重新路由
       → 产生新的 DispatcherDecision（类型由 L3 判断）

20 秒内没有回答：
  → TTS：「没关系，你可以之后再告诉我。」
  → 清除澄清等待状态，Orb 恢复原来的状态（idle 或 working）
```

### A.4 避免无限追问

```text
同一个问题最多追问 2 次；
第 3 次系统仍然判断不了 → TTS：「这个我理解不太好，你可以换个说法吗？」
→ 回到 idle，不再追问
```

## 10. 发给 L3 的上下文包（voice envelope）

调用 `routeToL3` 时必须附带完整的 `dispatcher_decision` 快照。L3 根据这些字段决定自己的行为，而不是靠 prompt 里的建议文字：

| 字段 | L3 的强制行为 |
|------|--------------|
| `acceptance_round: true` | 只能调受理白名单里的工具（§6.2） |
| `force_background: true` | 同上 |
| `prefer_direct_llm: true` | 走直连大模型路径，不走工具 |
| `inject_task_context: true` | system prompt 里追加后台任务简况 |
| `interrupt_verdict: ABORT` | 只调取消工具，不新开任务执行流程 |
| `target_task_id` | 取消/查询操作的对象 task_id |
| `clarification_handle` | 续答时带回，L3 合并上下文重新路由 |
| `awaiting_confirmation: true` | 本轮只输出确认问句，不调工具 |

## 11. 各类事件的 HUD 和 TTS 策略

| 事件类型 | HUD 显示 | TTS 播报 |
|----------|----------|----------|
| `progress`（进度更新） | 终端滚动 + 可选进度条 | 默认不念（用户不想听进度播报） |
| `completed`（任务完成） | 摘要 | 一句话（VAD 避让 + 播报队列） |
| `cancelled`（已取消） | 「任务已取消」 | 一句话 |
| `failed` / `partial`（失败/部分完成） | 执行摘要（ExecutionBrief） | 诚实的一句话，不回避 |
| 晨会（有遗留未完成任务） | HUD 列出任务列表 | 最多 2 句话 + 等用户确认 |

## 12. 系统降级与容错

> 系统不是每次都能正常工作。以下场景都需要有预定义的降级方案。**核心原则：任何组件出问题，都不能让聊天通道被堵住。**

### 12.1 分流器自身出错

| 场景 | 降级方案 |
|------|----------|
| 关键词规则出现异常 | 兜底判断为闲聊，`route_source=rule_fallback` |
| 小 AI 模型响应超时（>500ms） | 按关键词规则结果路由；后台记录这次 miss |
| 小 AI 模型返回了非法 JSON | 同上；置信度=0，当作模糊意图处理 |

**硬性要求**：分流器出任何错，都必须有一个默认的 `DispatcherDecision` 输出，不能让聊天通道卡住。

### 12.2 提交长任务时 L3 连不上

```text
提交后台任务请求失败（HTTP 5xx 或超时）：
  → 最多重试 2 次（间隔 1 秒、3 秒）
  → 仍然失败：
      a. 任务槽状态标为 FAILED
      b. TTS：「任务提交失败，可能是系统繁忙，请稍后再说一遍。」
      c. Orb 变 idle（不能卡在「工作中」状态）
      d. HUD 显示红色提示行
  → 聊天通道立刻可用（失败不影响后续说话）
```

### 12.3 受理轮 15 秒内 L3 没有回复

```text
→ 桌面强制中断前台执行（run_abort）
→ TTS：「我在处理，一会儿告诉你结果。」
→ 继续等待提交事件（如果提交指令已经发出去了）
  └─ 再等 10 秒还没有 → 按 §12.2 的失败流程处理
```

### 12.4 桌面重启后任务槽数据丢失（但后台还在跑）

```text
场景：桌面 App 崩溃重启，内存里的任务槽没了，但 L3 的后台 Worker 还在跑
  → 唤醒时调用 core:check_background_task 查一遍
  → 发现有运行中的任务 → 重建任务槽（状态=RUNNING_BG）
  → TTS：「后台有任务还在运行，我帮你恢复了状态。」
```

## 13. 端到端场景示例

### 13.1 长任务 + 后台进度 + 插嘴闲聊

```text
用户：「这目录 50 个 PDF 都摘要」
  → 分流：长任务
  → 立刻播「收到，这就去办。」+ Orb 变「工作中」+ 创建任务槽
  → L3 受理轮（白名单）→ 提交任务 → task_id=bg-001
  → HUD：[12:01] 扫描目录…  [12:02] 已处理 12/50 …
  → 聊天通道开启

用户：「今天吃什么」
  → 分流：闲聊，注入后台任务上下文（「PDF 12/50」）
  → L3 直连回答，顺带提到任务进度
  → TTS：「建议吃烤肉！顺便说，PDF 已经处理了 12 份了。」
  → Orb 回「工作中」
```

### 13.2 短任务超时自动升级

```text
用户：「读一下这个大文件」
  → 分流：短任务 → Orb 变「思考中」，5 秒计时器启动
  → 5 秒超时，L3 还在读文件
  → 桌面刷新 generation + Orb 变「工作中」
  → 立刻播：「这个要久一点，我改成后台，完成了叫你。」
  → 注入 VOICE_ESCALATE → L3 提交后台任务 → task_id=bg-002
  → 聊天通道释放
```

### 13.3 模糊意图触发澄清

```text
用户：「帮我处理一下」
  → 关键词规则没命中 → 小 AI 模型判断：AMBIGUOUS
  → Orb 变「澄清中（青白）」
  → L3 生成澄清句 → TTS：「你是要处理文件，还是处理邮件？」

用户：「文件」
  → 识别为 CLARIFY_REPLY → 带上澄清上下文发给 L3
  → L3 合并上下文重新路由 → 判断为短任务或长任务，正常执行
```

### 13.4 两个后台任务同时在跑，精确取消其中一个

```text
当前后台：[bg-pdf（名称=PDF摘要）, bg-resume（名称=简历分析）]

用户：「简历那个别弄了」
  → 关键词「简历」匹配 task_slot.title → target_task_id = bg-resume
  → 裁决：ABORT
  → 调用 core:cancel_background_task(bg-resume)
  → TTS：「好的，简历分析已停止。PDF 摘要还在继续。」
  → bg-pdf 继续运行，Orb 保持「工作中」
```

### 13.5 会话到期 + 再次唤醒

```text
（PDF 任务在后台跑，用户 60 秒没说话）
  → 语音会话到期
  → 任务不停，Orb 保持「工作中（慢呼吸）」；唤醒词监听恢复

用户：「嘿贾欣」
  → 新的语音会话创建
  → 检测到任务槽存在 → 自动播进度报告
  → TTS：「我还在，PDF 做到 35 份了，大概还要 1 分钟。」
  → Orb 从「工作中」变「监听中」（等用户继续说话）
```

## 16. 开发顺序（建议按这个顺序做）

| 步骤 | 内容 | 验收标准 |
|------|------|----------|
| **1** | `dispatchUtterance` 函数骨架，插入 doActualSend 之前；实现 Stage 0 关键词规则表 | STT 回调不再直调 doActualSend |
| **2** | 任务确认音 WAV + Orb working / clarifying 状态 | 判定后 500ms 内有声音反馈 |
| **3** | 长任务：本地 task_slot 创建 + 受理轮白名单强制执行 | 受理轮里调不了 fs_read 等工具 |
| **4** | 插嘴仲裁（ABORT/PARALLEL/STATUS）+ target_task_id 解析 | 后台跑着能聊天；能查进度 |
| **5** | 模糊意图澄清子态（附录 A） | 模糊句产生澄清问句，回答后正确路由 |
| **6** | `core:cancel_background_task` API + ABORT 完整闭环 | 取消有 API、有回调事件 |
| **7** | 结构化 `progress` 事件 + HUD 终端显示 | HUD 显示「12/50」而不是转圈 |
| **8** | 短任务超时升级（§6.4）+ 完成播报队列（§8.5） | 5s 超时有升级提示音；任务完成不打断说话 |
| **9** | 语音会话到期 + 重唤醒状态播报（§7.3）+ 晨会恢复（§7.4） | 到期不停任务；再次唤醒有进度播报 |
| **10** | 闲聊注入后台任务上下文（§8.4）+ 新任务并行确认（§9.4） | 闲聊顺带提任务；新任务有并行确认 |
| **11** | Stage 1 小模型分类、MODIFY 热修改 | 可选增强，第一版不做 |

**第一版可以不做**：小模型分类、MODIFY 热修改、新任务待确认队列。

## 17. 关键决策一览

| 问题 | 决策 |
|------|------|
| 这是主方案吗？ | **是** — 三条轨道 + 双通道并行 + 即时反馈 + 插嘴仲裁 |
| 第一版最重要的事？ | **聊天通道和任务通道物理隔开**，不是提高分类准确率 |
| 输出数据结构？ | **`DispatcherDecision` v1**，含 `target_task_id`、`clarification_handle` |
| 分流器插在哪里？ | **`dispatchUtterance` 函数，严格在 doActualSend 之前** |
| 长任务受理如何约束 L3？ | **宿主白名单强制执行**，不靠 L3 自觉遵守 prompt 建议 |
| 短任务超时怎么办？ | **播升级提示音 + 注入 VOICE_ESCALATE**，接力转长任务 |
| 意图模糊时？ | **澄清子态**，最多问 2 次，有超时兜底 |
| 闲聊时如何感知后台任务？ | **桌面端显式注入任务简况**，L3 自然带提 |
| 任务完成通知和 TTS 冲突？ | **播报队列 + VAD 检测**，不打断用户 |
| 如何停止后台任务？ | **`core:cancel_background_task`**（协作式取消，不强杀） |
| 会话到期但任务没完成？ | **会话到期不等于任务取消**，唤醒后自动汇报进度 |
| 系统出错？ | **每条路径有明确降级方案**，聊天通道不被阻塞 |

---

## 18. 一句话总结

**语音入口永远不被长任务堵死：分流器在真正发给 L3 之前完成判断；长任务受理轮白名单强制执行；短任务超时自动接力后台；意图模糊先澄清再执行；任务在后台跑，闲聊回复顺带提进度；完成通知排队不打断用户；会话到期任务继续跑，重新唤醒自动汇报。**
