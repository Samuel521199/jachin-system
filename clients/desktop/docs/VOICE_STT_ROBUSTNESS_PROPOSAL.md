# 语音识别容错与实体纠错方案（STT Robustness & Entity Correction）

> **状态**：设计稿（未编码）  
> **落地原则**：完整方案所列能力 **最终都要做**，按 §7 分 **先行 MVP** 与 **后续增强** 两层交付——**没有「砍掉不做」的模块**，只有 **先上线止血、再逐步补齐** 的顺序之分。  
> **方案边界（Codex）**：本文档是 **「端到端语音任务鲁棒性方案」**——目标是 **听错以后任务还能做对**；若问题定义仅是 **「提高 STT 字面准确率」**，还需配合 §4.17 音频链路、§4.1 热词、§4.19 二次识别等「让耳朵听更准」的能力，二者互补但不等同。  
> **触发案例**：用户说「请你帮我打开 Lark 然后发一条测试消息给 Vivian，内容是我今天要睡觉」  
> → STT 输出：`帮我打开 luck 给 viian 发一条消息内容是我今天要睡觉`（或 `lock` / `v薇m` 等变体）  
> → 系统直接用噪声文本执行 → `mcp:windows_open_app(luck)` → `FileNotFoundError`  
> **本质问题**：**不要把希望全压在 STT 模型上**——本案是中英混说 + 专有名词 + 任务执行 **强依赖实体名**；ASR 只要错一个实体，后面 Agent 就会走歪。缺的不是「更会听英文的耳朵」，而是 **听完之后把专有名词拉回业务世界的纠错脑子**（语音实体规范化 / Canonicalization）。  
> **最推荐路径**：STT 后面加 **语音实体纠错**，**禁止**把原始识别文本直接送进任务路由。  
> **本案关键矛盾**：IO reasoning 已看懂「应发消息」，结构化结果仍是 `app_control` + `app_name=luck`，`recipients` / `message` 为空仍放行  
> **关联文档**：`VOICE_OS_TOOL_INTENT_ROUTING_PROPOSAL.md`、`VOICE_INTENT_ROUTING_AND_TASK_ORCHESTRATION.md`  
> **诊断脚本**：`scripts/test_sensevoice_pure.py`（原生 SenseVoice，绕过 JVS/VAD）

## 1. 问题背景

### 1.1 语音到文字是有损转换

无论用哪家 ASR，语音转文字都是 **按声学概率猜出来的文字序列**，不是精确输入。常见失真：

| 失真类型 | 举例 | 原因 |
|----------|------|------|
| **同音/近音替换** | `Lark → luck/lock` | 音节相近，语言模型选更常见词 |
| **人名/专有名词出错** | `Vivian → viian` | 训练语料频次低，易缺字母 |
| **中英乱码** | `Vivian → v薇m / V薇 / 薇 m` | 英文被拆成字母 + 汉字 |
| **语言混合出错** | 中文句子里夹英文 App 名 | 中英切换点 ASR 最脆弱 |
| **停顿截断** | 「给…viian 发…」被 VAD 切开 | 静音检测 / 端点误判 |
| **口音/噪声** | 识别率整体下降 | 环境与发音 |

**关键前提**：每一句语音输入都应视为 **「可能有噪声的信号」**，而不是精确文字。当前系统没有这个前提。

### 1.2 为什么英文实体特别脆弱（SenseVoice Small）

当前 STT：**SenseVoice Small ONNX**（`funasr-onnx`，`data/models/voice/stt/SenseVoiceSmall-onnx/`），经 JVS（`voice_server`）推理。

| 弱点 | 人话 |
|------|------|
| **中文为主** | 设计目标是听懂中文句子，顺带支持英/日/粤/韩 |
| **业务名词不在训练集** | Lark、Vivian、Jachin 模型从未见过 |
| **量化损精度** | `model_quant.onnx` 英文边缘 case 更差 |
| **无热词注入** | 启动时未喂飞书联系人、已装 App 名 |
| **产品前置链路** | 48k→16k 重采样、VAD 截断、声纹裁剪可能进一步损伤英文词头/词尾 |

**结论**：关键不在于「让 SenseVoice 永远听对英文」，而在于让系统知道——在 **「打开应用」槽位** 里，`luck` 大概率是 **Lark**；在 **「联系人」槽位** 里，`viian` 大概率是 **Vivian**。指望 STT 永远听对 **不现实**；建好纠错脑子后 **仍能完成任务** **完全可行**。

### 1.3 典型失败样本

| 你说的是 | STT 听成的 | 后果 |
|---------|-----------|------|
| **Lark** | luck / lock / 拉克 | 找 `luck.exe` → FileNotFoundError |
| **Vivian** | viian / v薇m | 收件人槽为空 |
| Chrome | clone | 找不到应用 |
| VS Code | WS code | 找不到编辑器 |

**规律**：应用名 + 联系人名 + 专有名词 = ASR 最不可靠的三类实体，也是 Jachin 任务执行最依赖的三类槽位。

### 1.4 完整失败链（本案）

```
用户说：「帮我打开 Lark 给 Vivian 发一条消息内容是我今天要睡觉」
          ↓ STT（SenseVoice）
输出：「帮我打开 luck 给 viian 发一条消息…」
          ↓ 无缓冲带，字面直传 IO
app_name=luck, recipients=[], message="", missing_slots=[]
          ↓ IO 内部矛盾
reasoning: "应 lark_message_send"  vs  task_type: app_control
          ↓ 被「打开」绑架 + 快速路径 execute（置信 0.9）
route = windows_open_app(luck)
          ↓ 硬匹配 + 无 recovery
FileNotFoundError 透传用户；发消息目标被丢弃
```

**0 轮澄清、0 次改道**——差一个字母就是两个完全不同的目标。

### 1.5 被忽视的前半段：音频前置链路

SenseVoice 收到音频 **之前**，声音已经过多道处理——每一道都可能让信号变差，而本文档的纠错层无法补救「SenseVoice 根本没收到完整发音」的问题。

| 处理环节 | 做了什么 | 可能造成的问题 |
|---------|---------|--------------|
| **麦克风采集** | 系统麦克风录制原始 PCM | 底噪、远场衰减、回声未消 |
| **48kHz → 16kHz 重采样** | Tauri 客户端降采样后送 JVS | 重采样算法不当会引入混叠失真，损伤英文词头/词尾高频 |
| **VAD（端点检测）** | 静音检测，自动切割句子起止 | 句首/句尾的音节被「吃掉」——如「Lark」开头的 L 被截掉，SenseVoice 只收到「ark」；快语速时整词丢失 |
| **声纹过滤（说话人识别）** | 只保留「主人轨」，过滤他人声音 | 声纹模型配置不准时 **会把主人自己的话也过滤掉**，或把句尾截断 |
| **降噪** | 可选的前处理滤波 | 过激降噪消掉摩擦音（s/sh/f）、送气音，加重英文识别错误 |

**关键结论**：判断「为什么听错 luck」之前，必须先确认 VAD 和声纹过滤没有把正确发音截掉。否则纠错层再完善，也补不回「SenseVoice 根本没收到完整发音」。

**前置链路诊断方法**：同一句话分别用干净 WAV 文件（T1，绕开 VAD/声纹）和桌面 PTT 录音（T2，走完整链路）跑 STT，对比原文——

- T1 能听对，T2 听不对 → 问题在 **前置链路**（VAD / 重采样 / 声纹）
- T1 也听不对 → 问题在 **SenseVoice 本身**（模型能力 / 热词缺失）

### 1.6 方案边界：我们到底在解决什么

| 问题定义 | 本文档是否覆盖 | 说明 |
|---------|--------------|------|
| **听错专有名词 → 任务执行歪了**（luck 打开失败、viian 找不到人） | ✅ 核心覆盖 | 实体纠错 + Lexicon + 槽位校验 + 执行确认 |
| **听错后任务还能做对**（端到端鲁棒性） | ✅ 完整覆盖 | 五层全链路（§3.0） |
| **单纯提高 STT 字面准确率**（屏幕上显示的每个字都对） | ⚠️ 部分覆盖 | 靠 §4.17 音频链路、§4.1 热词、§4.19 二次识别、§4.15 换引擎；**纠错层不提升字面准确率，只提升任务成功率** |

**人话**：这份方案的重点不是「让 SenseVoice 永远听对 Lark」，而是「就算听成 luck，系统也知道你要的是 Lark，并且不会乱执行」。如果还要字面也准，音频链路和热词是另一条线，和纠错层 **一起做**，不是二选一。

## 2. 根因分析（十三项）

| # | 根因 | 人话 |
|---|------|------|
| 1 | **STT 输出当圣旨** | 无 suspect_tokens、无候选词，下游只看见「确定的 luck」 |
| 2 | **声学驱动不懂语义** | 不知道你装了 Lark、同事叫 Vivian |
| 3 | **缺 Domain Lexicon** | luck/viian 无别名映射 SSOT |
| 4 | **复合任务拆错** | 「打开」当主任务，忽略「给 X 发消息内容是 Y」 |
| 5 | **槽位校验虚设** | message 任务 recipients/message 皆空仍放行 |
| 6 | **工具硬匹配** | `windows_open_app("luck")` 精确找 exe |
| 7 | **缺上下文缓冲带** | STT 裸文本直连 IO |
| 8 | **reasoning ≠ route** | 说一套做一套，无一致性门禁 |
| 9 | **HIDCA 域错** | 发消息却标 `OS_CONTROL` 非 `WORKSPACE_LARK` |
| 10 | **无 Execution Recovery** | 打开失败不回头改道发消息 |
| 11 | **多轮上下文未用** | 上一轮刚说过 Lark，本轮 luck 不继承 |
| 12 | **VAD / 重采样损伤** | 句首句尾被截断，英文词头/词尾丢失，SenseVoice 拿到的已是残缺音频 |
| 13 | **声纹过滤误伤** | 声纹模型把主人自己的话过滤掉，或句尾截断，问题不在 STT 本身 |

## 3. 解决思路：纠错脑子优先，别只换耳朵

### 3.0 完整解决路线（五层全链路）

Codex 指出：本文档原版只覆盖了**中间和后半段**，**前半段**（音频质量 / VAD / 声纹裁剪）同样是 STT 精度瓶颈，不能跳过。完整路线如下：

```text
原始语音
    ↓
① 音频前置链路优化                ← 前半段：降噪、重采样质量、VAD 调参、声纹校准
    ↓
② SenseVoice STT                 ← 「耳朵」：可能听错，接受噪声
    ↓
③ 语音实体纠错 / 规范化           ← 「脑子」：规则 B → Lexicon → LLM C
    ↓
④ 意图路由：槽位校验 + reasoning 门禁 + 复合句目的优先
    ↓
⑤ 工具执行前确认 / Execution Recovery
```

**本文档的边界**：**原版覆盖 ③④⑤**，**Codex 补全了 ①** 和**通用中文语义错（非英文实体）**的覆盖。

**同一句子在系统内的两种形态**：

| 阶段 | 文本 |
|------|------|
| STT 刚输出（**不得进 Router**） | `帮我打开 luck 给 viian 发一条消息内容是我今天要睡觉` |
| 规范化后（**才进任务系统**） | `请帮我打开 Lark，然后发一条测试消息给 Vivian，内容是「我今天要睡觉」` |

### 3.1 三轨闭环：全部必做，按顺序实施

```text
轨道 0（最先做）：清源 — 音频前置链路质量（VAD、重采样、声纹）
轨道 B（紧接着做）：纠偏 — 实体纠错 + 路由 + 执行容错
轨道 A（最后做）：提升 — 热词、引擎评估/替换
```

| 轨道 | 实施阶段 | 说明 |
|------|---------|------|
| **0：音频前置链路** | **阶段零**（Phase 0-A、0-B） | 前置链路有问题时，STT 拿到的就是残缺音频；**纠错层补不回**；优先排查 |
| **B：实体纠错 + 执行容错** | **阶段一～三**（Phase 1～14） | 就算换更强 STT，专有名词仍会错；此轨道是核心止血 |
| **A：STT 输入优化** | **阶段四**（Phase 9、16） | 热词 + 全链路 Eval + 引擎评估/替换；轨道 B 跑通后实施 |

**落地顺序（与 §7 对齐，全部为必做）**：

1. **阶段零**（Phase 0-A、0-B）：音频前置链路诊断 + 普通中文语义兜底 — **清源，排查是 STT 问题还是前置链路问题**
2. **阶段一**（Phase 1～6）：规则 B + Lexicon + 槽位校验 + UX 止血 + 工具软匹配 — **止血**
3. **阶段二**（Phase 7～14）：LLM 洗衣机 C、suspect_tokens、多轮上下文、纠错透明度、主动教导、规则生命周期、Fast Path、延迟监控
4. **阶段三**（Phase 15）：真实录音 Eval（T0～T4）— **验收门禁**
5. **阶段四**（Phase 9、16）：热词注入、STT 引擎评估（不达标则换引擎或云端 fallback）

### 3.2 三道手术（STT 之后、Router 之前，难度从低到高）

原生 SenseVoice **不认识业务名词**。在 STT 与意图路由之间必须加处理层：

| 手术 | 人话 | 实施阶段 |
|------|------|---------|
| **B：规则 + Lexicon** | 槽位感知替换 | **阶段一**（Phase 3，最先做） |
| **C：LLM 洗衣机** | 规则盖不住的间接说法、复杂句 | **阶段二**（Phase 7，B 完成后做） |
| **A：热词增强** | 识别前加权，Lexicon 导出喂 STT | **阶段四**（Phase 9，纠错层跑通后做） |

**铁律**：**STT 裸输出永远不能直连意图路由器**。阶段一用 B+Lexicon 先止血；**LLM C、热词 A 均为后续必做步骤**，不是可跳过项。

### 3.3 四道防线 × 三层能力（互补视角）

**四道防线（按位置）**

| 防线 | 位置 | 实施阶段 |
|------|------|---------|
| ② 大脑 | **语音实体纠错**（B 规则 + Lexicon + C LLM） | 阶段一～二 |
| ③ 底层 | 工具软匹配 | 阶段一 |
| ④ UX | 降级、轻确认、Recovery、纠错透明度 | 阶段一～二 |
| 路由补强 | IO：复合句、槽位、reasoning 门禁 | 阶段一 |
| ① 前端 | STT + 热词 | 阶段四 |

**三层能力（按职责）**：语音容错 → 意图路由 → 执行闭环。**三道防线缺一即方案未完成**。

## 4. 方案详解

### 4.1 手术 A：热词增强（Hotwords Boosting）—— 阶段四必做

SenseVoice / FunASR 推理时可传 **热词表 + 权重**，在声学概率接近时 **帮模型打破平局**：

```json
{ "Lark": 20, "飞书": 20, "Vivian": 20, "Jachin": 20, "Codex": 15, "Chrome": 10 }
```

| 词表来源 | 更新时机 |
|---------|---------|
| 已装 / 常用 App | 启动扫描 |
| 飞书通讯录 | 登录后同步 |
| Jachin 专有词 | 固定 |
| 用户自定义 | 设置页 |

**接入点**：`voice_server/services/stt_service.py`；落地前用 `test_sensevoice_pure.py` 验证 `hotword` 参数。  
**预期**：已在词表内的实体，误识别率 **显著下降**（经验 40～70%，须 Eval 实测）。  
**局限**：盖不住中英乱码；**不能替代后处理纠错层**（B/C）。  
**定位**：Phase 9 / 阶段四——**实体纠错层（阶段一～二）跑通后实施**；从 Lexicon 经 `export_for_stt()` 动态生成，**必做**。

### 4.2 手术 B：规则 + Lexicon — **阶段一（最先实施）**

#### 4.2.0 STT 输出前清洗（实体纠错的入口预处理）

在 Lexicon / 规则纠错 **之前**，先做一轮轻量文本清洗，目的是去掉 STT 产生的「噪声尾巴」，降低路由被无效字符带偏的概率。**注意：这一步只清洗格式噪声，不改实体名、不改正文语义。**

| 清洗类型 | 举例 | 处理方式 |
|---------|------|---------|
| **表情符号尾巴** | `我今天要睡觉😔` | 去掉结尾表情（正文保留文字） |
| **重复口头语** | `你好你好帮我打开 Lark` | 合并连续重复词 |
| **无意义语气词** | `那个那个那个…帮我` | 去掉句首无意义语气词堆叠 |
| **中英字母分裂** | `v 薇 m` → `Vivian`（Lexicon 接力） / `m d` → `md` | 字母 + 汉字组合先合并，再交给 Lexicon 识别 |
| **多余标点/空格** | `帮，，我 打开  Lark` | 规范化标点和空格 |

**边界**：这一步 **不做语义判断**，不碰实体名（交给 §4.2 主体和 Lexicon），不碰 message 正文内容（铁律）。作用是让后续规则/Lexicon 拿到更干净的文本，而不是一堆奇怪字符。

---

阶段一 **最先落地** 的三件事（覆盖本案 luck/viian）：

| 规则 | 条件 | 纠成 |
|------|------|------|
| App 槽 | `luck` / `lock` / `拉克` + **「打开/启动」或飞书语境** | **Lark** |
| 联系人槽 | `viian` / `vivien` / `v薇m` + **「给/发给」语境** | **Vivian** |
| 槽位门禁 | `message_send` **缺 recipient 或 message** | **禁止 execute** |

再加 UX 止血（not_found 人话澄清）；LLM 洗衣机在阶段二 **必做**，但 **阶段一不依赖 LLM**。

热词解决「听成另一个英文词」；**中英乱码** 用规则更快。  
**核心原则：上下文纠错，不要全局乱替换。**

| 用户说的 | STT 可能吐的 |
|---------|-------------|
| Vivian | viian、v薇m、V薇 |
| Lark | luck、lock、拉克 |

**槽位感知：只在对应句法位置才替换**

| 句法模式 | 噪声示例 | 才纠成 | 反例（禁止全局替换） |
|---------|---------|--------|---------------------|
| `打开 {X}` / `启动 {X}` | luck、lock | **Lark**（应用槽） | 句中其他位置的 luck 不自动改 |
| `发给 {X}` / `给 {X} 发消息` | viian、v薇m | **Vivian**（联系人槽） | 「运气 luck 不错」里的 luck 不动 |
| `发给 {X} 组` / 项目语境 | jacking | **Jachin**（项目槽） | — |
| **`内容是 {…}` / message 正文** | luck、viian 等 | **禁止修改** | 见下条铁律 |

**铁律：只纠 app / contact / project 槽，禁止纠 message content 槽**

落地时必须写进代码与单测，不能只做「文档里提了槽位感知」：

| 用户说（STT） | 应纠正 | 正文必须保持 |
|-------------|--------|-------------|
| 给 Vivian 发消息，**内容是 luck 很好笑** | 收件人 → Vivian | 正文仍是 `luck 很好笑`，**不能把 luck 改成 Lark** |
| 打开 luck 给 viian 发消息，内容是我今天要睡觉 | luck→Lark，viian→Vivian | `我今天要睡觉` 一字不改 |

纠错层 **先切槽位**（app / recipient / message_body），**仅在实体槽内** 做替换；`message_body` 区间 **只读、不替换**。

```text
STT 原始输出
  ↓ 1. 句型 / 槽位定位（打开 X？发给 X？）
  ↓ 2. 仅在对应槽位内做正则 / 编辑距离 / Lexicon
  ↓ semi_clean_text + rule_corrections[] + slot_hints[]
```

**规则示例**（持续沉淀，非写死）：

| 模式 | 替换为 | 备注 |
|------|--------|------|
| `v薇m`、`V薇`、`薇 m` | Vivian | 中英乱码 |
| `luck`（语境含发消息/飞书） | Lark | 语境门控 |
| `viian`、`vivan` | Vivian | 编辑距离 1～2 |

原则：**只修有把握的**；命中写 `rule_corrections[]`；与 Lexicon 同一 SSOT；3 次复现入库。

### 4.3 手术 C：LLM 前置洗衣机 — **阶段二必做（须极度克制）**

> **阶段一**：B + Lexicon 先止血（不依赖 LLM）。  
> **阶段二**：LLM 洗衣机 **必做**——处理规则 + 词典搞不定的间接说法、复杂句、中英乱码边缘 case。

> **Codex 红线**：LLM **只能做结构化实体建议，不能自由重写整句**。尤其 **message 正文必须只读**——否则「内容是 luck 很好笑」被改成「Lark 很好笑」就是 **新事故**，比不纠错更糟。

**LLM 允许做的（结构化输出）**：

```json
{
  "entity_suggestions": [
    { "slot": "app", "original": "lock", "corrected": "Lark", "confidence": 0.92 },
    { "slot": "recipient", "original": "v薇m", "corrected": "Vivian", "confidence": 0.88 }
  ],
  "message_body": null,
  "needs_clarify": false
}
```

**LLM 禁止做的**：

| 禁止行为 | 反例（新事故） |
|---------|--------------|
| **自由重写整句** | 把用户原意改写成 LLM 认为「更通顺」的句子 |
| **修改 message 正文** | 「内容是 luck 很好笑」→「内容是 Lark 很好笑」 |
| **添加用户没说的词** | STT 没提到收件人，LLM 凭空补一个 |
| **删除否定词** | 「不要打开 Lark」→「打开 Lark」 |

**实现约束**：
- LLM 输出 **必须是结构化 JSON**（实体槽位 + 建议值），**不是**一段自由文本
- 应用层 **只采纳 entity_suggestions**，按槽位合并；`message_body` 区间 **代码层硬拦截，LLM 输出不可覆盖**
- LLM 与规则冲突 → **clarify**，禁止静默执行
- 超时 / 报错 → **零等待降级** B + Lexicon（§9.1）

```text
STT：「请帮我打开 lock 然后给 v薇 m 发送一条消息，内容是 luck 很好笑」
  ↓ B 规则清洗（app/recipient 槽）
  ↓ C LLM（只输出 entity_suggestions，message_body=null）
输出 entity_suggestions：lock→Lark, v薇m→Vivian
正文保持：「luck 很好笑」  ← 一字不改
  ↓ Router（只吃 buffer_corrected）
主任务 = lark_message_send
```

| 项 | 建议 |
|----|------|
| **模型选型** | **极小、极快**——本地 Qwen 1.5B / 4B 量化版，或专用纠错小模型；**禁止**复用 L3 的 Qwen3.5-Plus |
| **输出格式** | **结构化 JSON only**；禁止返回自由文本整句 |
| 延迟 | **硬上限 500ms**；见 §4.10、§9.1 延迟雪崩 |
| 熔断 | **Timeout 一到立即降级** B + Lexicon，不等待、不重试同模型 |
| 安全 | LLM 与规则冲突 → clarify，禁止静默执行 |
| 日志 | 保留 `stt_raw`、`buffer_corrected`、`corrected_entities[]`、`correction_latency_ms`、`correction_fallback_reason` |

**与规则关系**：LLM 主路径泛化；规则兜底 + 交叉校验。串联顺序：**B → Lexicon → C**。

### 4.4 STT 输出结构升级（suspect_tokens）

不只传一句 `final_text`：

```json
{
  "raw_text": "帮我打开 luck 给 viian发一条消息…",
  "normalized_text": "帮我打开luck给viian发一条消息…",
  "suspect_tokens": [
    { "token": "luck", "candidates": ["Lark", "飞书"], "reason": "phonetic_near_app" },
    { "token": "viian", "candidates": ["Vivian"], "reason": "contact_fuzzy" }
  ],
  "channel": "voice_stt"
}
```

下游 **不得** 只读 `normalized_text` 当事实。

### 4.5 统一实体库（Domain Lexicon SSOT）

本地维护 **应用 / 联系人 / 项目** 三类实体及别名——供热词、规则清洗、LLM、工具层共用：

```json
{
  "apps": {
    "Lark": ["lark", "luck", "lock", "拉克", "飞书"],
    "Codex": ["codex", "code x", "扣得克斯"],
    "Chrome": ["chrome", "clone"]
  },
  "contacts": {
    "Vivian": ["vivian", "viian", "vivien", "薇薇安", "微微安", "v薇m"]
  },
  "projects": {
    "Jachin": ["jachin", "jacking", "加勤", "嘉钦"]
  }
}
```

canonical 名 → 别名列表；**纠错时永远归一到 canonical**。

**模糊匹配：三类信号综合打分**（App / 联系人皆适用）

| 信号 | 示例 | 权重逻辑 |
|------|------|---------|
| **字符串相似度** | viian ≈ vivian（编辑距离 1） | 字面接近 |
| **发音相似度** | luck ≈ lark（音近） | 中英混说常见 |
| **业务上下文** | 「打开 X」→ X 更可能是 **应用名**；「发给 X」→ X 更可能是 **联系人** | 槽位感知 |

三者合起来定置信度，**不要单靠编辑距离硬猜**。

**来源优先级（比「一个 JSON 文件」更重要）**

实体解析冲突时，按来源 **从高到低** 采信：

```text
用户手动别名  >  最近会话已确认实体  >  飞书通讯录  >  系统默认词表
```

| 情形 | 处理 |
|------|------|
| 两个 Vivian、重名、已离职仍 inactive | **必须澄清**（「发给哪个 Vivian？」），禁止编辑距离硬猜 |
| 手动别名与通讯录冲突 | **以手动为准** |
| 会话里 30 秒前确认过 Vivian | 本轮 viian 可高置信归一 |

JSON 只是 **存储形态**；每条别名应带 `source`、`active`、`last_confirmed_at` 等元数据，而不只是字符串列表。

**维护来源**：已装 App 扫描、飞书通讯录、用户手动别名、纠错反馈（3 次同向确认写入）。见 §9.2 自动同步。

**⚠️ 保鲜机制（必做，见 §9.2）**：实体库上线时很好用，但 **同事入职离职、项目改名** 后，若靠手改 JSON 会迅速腐烂。必须预留 **自动同步**，不能当静态配置文件一次性写完就忘。

**纠错置信度分级**：

| 相似度 | 处理 |
|--------|------|
| 完全匹配 | 直接用 |
| 编辑距离 ≤1 | 静默纠错 + 回复说明 |
| 编辑距离 2～3 | 纠错 + 询问确认 |
| >3 且无历史 | 澄清，不猜 |

### 4.6 意图路由补强

**复合句**：「打开 X + 给 Y 发消息 + 内容是 Z」→ 主任务 **message_send**，打开 X 降为 optional_precursor。

**任务优先级**：发送/创建/删除/提交 **>** 打开/切换/进入。

**槽位强校验**（按 task_type 绑定）：`message_send` 缺 recipient 或 message → **禁止 execute**。

**reasoning ↔ route 一致性门禁**：不一致 → FAIL → 重新路由或 clarify。本案 **必须被拦**。

**HIDCA**：域以主任务目的为准；发消息 → `WORKSPACE_LARK`。

### 4.7 工具层软匹配 + Execution Recovery（**与 Router 共用 Lexicon**）

Router 修好了，**工具层仍会炸**——若工具各自硬匹配，前面白做。

```text
windows_open_app("luck")
  → 读 **同一份 Lexicon** → Lark
  → 解析为实际启动目标：可能是「飞书」DisplayName、特定安装路径，**不一定有 Lark.exe**
  → 或句含「给 X 发消息」→ 改走 lark_message_send
  → 仍失败 → 「您是想打开飞书（Lark）吗？」
  → 禁止 FileNotFoundError 透传
```

**原则**：

- **Lexicon SSOT 三处同吃**：纠错 B、意图 IO、**MCP 工具执行**（`windows_open_app`、`lark_message_send` 联系人解析）  
- 手段失败不覆盖目的；Recovery 最多 1～2 次；记 `[StrategyShift]`

### 4.8 UX：降级、轻确认、主动透明

**铁律：外部副作用动作必须确认**

发飞书、发邮件、删文件等——**即使 viian 已成功纠成 Vivian，也不能静默执行**。

| 动作类型 | 能否高置信静默执行 |
|---------|-------------------|
| **打开本地 App**（无对外副作用） | 可以（纠错后说明即可） |
| **发消息 / 发邮件 / 删改文件** | **不可以** — 必须确认 |

**禁止**：`failed:FileNotFoundError(2, '系统找不到指定的文件。'…)`  
**应当**：「没有找到 luck，您是想打开 **Lark（飞书）** 吗？」

**「何时问、何时静默」决策表**：

| 情形 | 处理 |
|------|------|
| 实体完全匹配 + 无 suspect + **local 打开 App** | 可静默执行，主动告知 |
| **任意发消息 / 邮件 / 删文件** | **必须确认**（与置信度无关，默认铁律） |
| **高置信自动执行** | 仅 **local 打开类**；`luck` 在「打开」后 + Lexicon 唯一候选 → 可静默纠成 Lark 并打开 |
| suspect + 编辑距离 ≤1 + local 操作 | 静默纠错 + 说明 |
| 会话历史已有相同实体 + local 操作 | 置信提升 |
| 候选 ≥2 个 Vivian / 重名 / inactive | 列出让用户选，**禁止硬猜** |
| 编辑距离 >3 且无历史 | 直接澄清 |

**低置信度二次确认示例**（external 操作）：

> 我理解为：打开 **Lark**，给 **Vivian** 发消息：「我今天要睡觉」。确认发送吗？

**副作用预览**：发送前展示 **最终对象 + 内容**；用户应能一眼核对。

### 4.9 多轮上下文与冷启动

**多轮上下文**：纠错层参考近 **5 条** 会话历史——若上一轮已出现 Lark/Vivian，本轮 luck/viian 置信度直接提升，可静默纠错而不用再问。

**冷启动（Lexicon 为空时）**：新用户刚安装、或第一次说某个名字，Lexicon 里还没有这条映射。此时不能乱猜，应该：

| 场景 | 处理方式 |
|------|---------|
| STT 输出完全在已知词表里 | 正常执行 |
| 识别出可疑 token，但 Lexicon 无对应 | 降级：**原样传 IO + 标记 suspect**；IO 用通用语义理解，不走 Lexicon 硬替 |
| 任务强依赖实体（发消息必须有收件人） | 主动问：「您要发给谁？」补槽，而不是猜 |
| 打开 App 但找不到 | 人话澄清（§4.8），并提示「您可以告诉我以后『luck』就是指哪个软件」（见 §4.13） |

**冷启动加速**：每次成功确认后立刻写入 Lexicon，**下一轮就不是冷启动了**。飞书通讯录同步（§9.2）是最快的 contacts 热身路径。

### 4.10 纠错透明度：让用户看见系统改了什么

纠错是在背后悄悄做的事——**用户不知道系统改了什么，就无法发现纠错出错**。这是隐患，必须对用户可见。

**原则：每次纠错都要告知，但不打断操作**

| 纠错类型 | 展示位置 | 展示内容 |
|---------|---------|---------|
| 静默纠错（高置信 + local 操作） | 回复里小字说明 | `「已将 luck 理解为 Lark」` |
| 轻确认（外部副作用） | 确认弹窗 | `「给 Vivian 发送：我今天要睡觉。确认吗？」` |
| 低置信 / 候选≥2 | 内联选择卡 | `「我听到的是 viian，您是指：① Vivian ② Vian Huang？」` |
| 纠错结果最终 | 消息气泡下方 | 可折叠标注 `[原始：帮我打开 luck…]` |

**展示细节**：
- 不要全量显示 raw STT（用户不关心，且干扰阅读）——**只显示被纠的实体**
- 用户点「不对」或「撤回」→ 进入 §4.13 主动教导流程，同时撤销操作
- 纠错说明文字要像 **助理在说话**（「我把 luck 理解为 Lark」），而不是技术日志（「entity_correction: luck→Lark」）

**反面教训（禁止）**：纠错后 **静默执行 + 无提示** ——用户看到飞书消息发出去了，但不知道 Jachin 是怎么理解的，出错了也不知道从哪里改。

### 4.12 延迟预算与「延迟雪崩」

**现状（Benchmark 参考）**：语音链路里 **L3 意图路由** 单独平均已可达 **~5.5 秒**（见 `data/voice_latency_bench/`、`scripts/benchmark_voice_pipeline_latency.py`）。用户本来就觉得慢——纠错层 **绝不能再叠一个慢 LLM**。

| 层 | 预期延迟 | 说明 |
|----|---------|------|
| suspect_tokens | < 5ms | 规则扫描 |
| 规则纠错 B | < 20ms | 确定性 |
| **LLM 纠错 C** | **150～500ms 硬顶** | 超时 **必须** 熔断，见 §9.1 |
| 合计新增（纠错层） | 约 200～600ms | **不含** L3 那 5.5s |

**落地风险**：若实现时 **误用 Qwen3.5-Plus** 做洗衣机 C，单次纠错可能 **1～3 秒+**，整体体验雪上加霜——这叫 **延迟雪崩**。

**硬性对策**：

```text
手术 C 启动（小模型，max_tokens 极简 prompt）
    ↓
  等待，上限 500ms（可配置，建议默认 400ms）
    ↓ 超时 / 报错 / 模型未加载
立即降级：手术 B + Lexicon（<20ms），标记 correction_fallback=timeout
    ↓
external 操作：强制轻确认（因未过 LLM 确认）
```

**验收**：纠错层 P99 **< 500ms**；降级路径须覆盖 **100%** 超时场景（Eval 注入慢模型/mock timeout）。

感知上：STT 结束 → 规范化完成 **< 1 秒**（不含 L3）；L3 慢是另一个优化课题，**不能用大模型纠错去换准确性而拖死首响应**。

### 4.13 用户主动教 Jachin（主动 Lexicon 建立）

> **动机**：系统从反馈里慢慢学很好，但有时用户知道自己接下来要说很多次某个名字——比如新同事 `Bartholomew`，SenseVoice 肯定听不对。让用户主动「提前教」比系统被动纠错要高效得多。

**三条触发路径**：

| 触发时机 | 交互 | 写入 Lexicon |
|---------|------|------------|
| 任务失败后，App/联系人找不到 | Jachin 说：「没找到 luck，您是想指哪个应用？以后我记住。」 | 用户回复 → 写入 alias |
| 用户主动说：「以后 luck 就是 Lark」 | 系统解析 `teach_alias` intent → 确认「好的，我记住了：luck = Lark」 | 立即写入，标记 `source=user_manual` |
| 设置页「我的别名」 | 图形化管理：列出现有别名、增删、优先级 | 用户保存 → 全量覆盖个人 Lexicon |

**「以后 luck 就是 Lark」** 必须是一等公民的 intent，不能靠碰运气被解析为 `open_app(luck)`。需要在 IO 层加 `teach_alias` 路由规则。

**边界**：
- 用户别名 **只影响自己的 Lexicon**（多用户 / 多租户不共享）
- 同名冲突时，用户手动 = 最高优先级（见 §4.5 来源优先级）
- 批量导入：设置页从 Lark 通讯录批量选词写入 Lexicon（Phase 12 一并交付）

### 4.14 规则表的生命周期管理

> §4.2 说「规则持续沉淀」——**但谁来加、从哪来、怎么验证、怎么下线？** 没说清楚的规则表最后会成黑洞。

**规则来源**（按可信度排序）：

| 来源 | 条件 | 动作 |
|------|------|------|
| **用户主动教** | `source=user_manual` | 直接写入，最高优先 |
| **连续 3 次相同纠错确认** | 用户说「是的，luck 是 Lark」≥3 次 | 自动写入通用规则，标记 `auto_confirmed` |
| **开发者/运营手动维护** | 高频误识别、已知乱码模式 | PR 入库；必须附说明和测试用例 |
| **实验性（待确认）** | 单次反馈 | 暂存为 candidate；**累计 3 次同向确认后自动入库**（见上条） |

**规则下线**：
- 连续 30 天未命中 → 标记 `stale`，提醒人工审查
- 被用户手动否定（「不对，luck 不是 Lark」）→ 降权或失效
- SenseVoice 升级后，之前补丁性规则可能已无必要 → 重测后考虑移除

**防规则冲突**：
- 同一 token 有多条规则时 → 按优先级链：`user_manual > auto_confirmed > dev_manual`
- 新规则入库前跑全量文字 Eval（§8.1）；命中样本覆盖 ≥3 条、误伤 = 0 才入

**人话**：规则表不是写完就扔的配置文件，是需要持续打理的活词典——它的健康度直接决定纠错层的可靠度。

### 4.15 体验层与 STT 引擎（阶段四）

- 引导用户说 **「打开飞书」** 而非「打开 Lark」（产品文案兜底，与热词并行）
- **阶段四必做**：热词调优、非量化 SenseVoice 对比、云端 ASR fallback 方案评估
- Phase 16：**必跑** Eval 50 条；recover 率仍 < 85% 则 **必须** 换引擎或启用云端 fallback

### 4.16 Fast Path 收紧（语音场景）

| 条件 | 键盘 | 语音 STT |
|------|------|---------|
| 置信阈值 | ≥ 0.80 | ≥ **0.85** |
| 过规范化层（至少 B+Lexicon） | 建议与语音一致 | **必须** |
| 过 LLM 洗衣机 C | 阶段二完成后 **必须**（语音） | 阶段二完成后 **必须** |
| suspect 已处理 | 阶段二完成后 **必须** | **必须** |
| 槽位强校验 | 必须 | **必须** |
| reasoning ≡ route | 必须 | **必须** |
| external 直接执行 | 视置信 | **轻确认** |

本案教训：置信 0.9 + 未过缓冲带 = **加速失败**。

### 4.17 音频前置链路优化（阶段零 Phase 0-A）

> **Codex 补充**：本文档原版聚焦的是「听错以后怎么纠偏」，但前置链路决定了 SenseVoice 收到的是什么——如果音频在进 STT 前已经残缺，纠错层再强也没法凭空还原。

**本节目标**：确保 VAD、重采样、声纹过滤不会成为 STT 精度的瓶颈。

#### 4.17.1 VAD（端点检测）调参

**常见问题**：

| 症状 | 原因 | 如何发现 |
|------|------|---------|
| Lark 识别成 ark / uck | VAD 激进，句首静音阈值太低，L 或 La 被截掉 | T2 比 T1 准确率低；`test_jvs_voice.py` 可见原始截图起点 |
| 快语速句子后半段丢失 | VAD 端点判断太早 | 同一句话慢说 T2 能过、快说不行 |
| 整句被吃掉 | 声音太小、远场时 VAD 误判全段为静音 | T2 输出为空，T1 可识别 |

**解决方向**：
- 调 VAD 静音阈值（建议保守，宁可多带点静音进 STT，也不截发音）
- 句首保留至少 100ms 缓冲；句尾保留至少 200ms 缓冲
- 评测指标：T2 vs T1 的 STT 相似度，**期望差距 < 5%**（差距大说明 VAD 是问题）

#### 4.17.2 重采样质量

**问题**：Tauri 客户端把系统麦克风 48kHz 降采样到 16kHz 送 JVS，使用简单的线性插值会引入混叠失真，英文高频音（s/sh/f/th）受损最大。

**解决方向**：
- 使用带低通滤波的高质量重采样算法（如 `rubberband`、`sinc` 插值，而非简单 Linear）
- 评测方法：对比同内容的原始 48k WAV 降采样前后 SenseVoice 结果

#### 4.17.3 声纹过滤策略（安保模式 vs 陪伴态）

**旧策略问题**：统一对所有场景做声纹主人轨过滤，阈值过严时会把主人自己的话或句尾截断。

**新策略：按场景分级**

| 场景 | 声纹策略 | 原因 |
|------|---------|------|
| **严格安保模式**（可选启用）| 强制主人轨过滤，只采信声纹 > 阈值的片段 | 多人环境/敏感操作 |
| **普通陪伴态**（默认）| 先跑 **全轨 STT**，再用声纹 **标注** 哪段是主人，结果加权而非过滤 | 避免误伤主人话 |

**主人轨过短/切得太碎时的回退**：

- 主人轨总时长 < 200ms，或被切成 3 段以上 → **直接回退全轨 STT**，不做声纹过滤
- 声纹模型不自信（相似度 0.4～0.6 灰区）→ 不过滤，标记 `voice_uncertain=true`，触发低置信路径

**两人重叠说话时**：

- **不要硬拼接**两人的 STT 结果（会产生语义混乱的垃圾文本）
- 检测到重叠说话 → **主动提示「我没听清，请再说一遍」**，比猜错执行更好

**注册样本要求**：
- 主人声纹注册样本 ≥ 5 条，覆盖不同语速、情绪、远近场
- 评测方法：同一句话有/无声纹过滤两路对比，STT 准确率不应有差异

#### 4.17.4 麦克风增益与录音质量

这是经常被忽视的项，问题不在软件算法，而在采集层：

| 问题 | 症状 | 排查方法 |
|------|------|---------|
| **增益过高** | 波形削波，STT 听到一团噪声 | 录音波形超过 0dBFS；WAV 波形顶部截平 |
| **增益过低** | 声音太小，VAD 误判全程静音 | WAV 波形幅度 < 10%，T2 输出为空 |
| **自动增益（AGC）** | 说话声音变化时增益突变，引入音量跳变，ASR 以为说了两个人 | 同一句话录音波形振幅忽大忽小 |
| **回声消除过激** | 消掉自己说话的声音（如用扬声器播放时） | 与耳机收音对比，扬声器收音 STT 准确率显著更低 |
| **录音过短 / 静音过多** | VAD 误判说话人停止 → 截断句子 | WAV 时长 < 预期；或开头有超过 500ms 静音 |

**解决方向**：
- 采集前做 **增益标定**（建议 RMS 在 -20dBFS 附近）
- 禁用或弱化 **AGC**（自动增益控制），保持增益稳定
- 排查是否有 **系统级回声消除**（Windows 音效增强）影响 Tauri 麦克风输入

#### 4.17.5 降噪策略

- 轻降噪（去底噪）优先于重降噪（消摩擦音），**宁可留点底噪进 STT，也不消英文辅音**
- 远场 / 背景音场景下，重降噪可能适得其反：**开关需可配置，不强制全开**
- 降噪处理造成音色变形的检验：用同一 WAV 降噪前后分别跑 T1，若准确率下降 → 降噪策略过激

**阶段零 Phase 0-A 交付物**：
1. T1 vs T2 对比诊断报告（每条样本：VAD / 重采样 / 声纹 / 降噪逐层 diff）
2. VAD 静音阈值调优后的 A/B 实测结果
3. 重采样算法升级确认或保留原实现的决策留档
4. 录音增益/AGC/回声消除排查结论

### 4.18 普通中文语义错的兜底（阶段零 Phase 0-B）

> **Codex 补充**：本文档重点是英文实体和专有名词，但 SenseVoice 在纯中文句子里也会犯错——如「天空是紫的」被识别成「天空是次的」、「我要开飞机」和「我要开会」在快语速下混淆、「不要」与「要」被截成只剩「要」。这类错误没有 Lexicon 可以纠，需要另一套兜底。

**中文语义错的特征**：不是实体名称错（Lark → luck），而是 **整体语义跑偏**，实体本身不在纠错层的射程内。

**三类典型中文错**：

| 错误类型 | 举例 | 症状 |
|---------|------|------|
| **否定词丢失** | 「不要打开 Lark」→ STT「要打开 Lark」| 任务完全反向 |
| **同音/近音混淆** | 「开飞机」vs「开会」/ 「睡觉」vs「谁叫」 | 意图完全不同 |
| **数词/量词失真** | 「三天后」→「三点后」/ 「下午三点」→「下午三天」 | 时间槽位错误 |

**兜底策略**（与英文实体纠错不同，不用 Lexicon，而用语义确认）：

1. **否定词保护**：IO 层对「不要 X」「不需要 X」「不用 X」做专项提取，**禁止语义解析把否定词丢失**；怀疑丢失时 → 触发轻确认
2. **高风险操作语义确认**：发消息、删文件、支付、拨打电话等 **不可逆操作**，无论中英文，**执行前必须展示主语 + 动作 + 对象确认**（与 §4.10 外部副作用确认对齐）
3. **意图置信过低时主动澄清**：IO 路由置信 < 0.7 且检测到「中文句子整体偏离期望域」时，触发澄清询问而非猜着执行
4. **Eval 中文基准集**：建立 50 条纯中文 T0 用例（含否定词、时间、数量词等易错模式），覆盖回归测试（Phase 0-B 交付）

**边界说明**：普通中文语义错 **不应** 走实体 Lexicon 路径，**不要** 在消息正文里做中文语义「纠错」——用户正文里说「我觉得天气不好」不是识别错，**禁止改**（与 §4.2 铁律一致）。

**阶段零 Phase 0-B 交付物**：
1. IO 层否定词保护逻辑
2. 纯中文语义错兜底 Eval 样本集（50 条，含 T0 文字用例）
3. 意图置信低时的澄清触发阈值配置

### 4.19 高风险场景二次识别（阶段零 Phase 0-C）

> **Codex 新增**：对于低置信或高风险句子，不要只信一次 STT 结果——本地 SenseVoice 先快速跑，命中高风险场景时再用更强的模型或云端复核。成本不高，但能大幅减少高风险操作的误识别率。

**核心思路**：两遍不是每句都做，**只在真的需要的时候做**。

#### 4.19.1 触发条件（满足任一即触发二次识别）

| 触发条件 | 说明 |
|---------|------|
| **置信度低** | STT 本地置信分 < 0.7（或 suspect_tokens 比例 > 30%） |
| **高风险意图** | 发消息、删文件、支付、拨打电话 **任何不可逆操作** |
| **关键实体模糊** | 识别出 `luck` / `viian` / 乱码等疑似专有名词噪声 |
| **否定词出现** | 句子含「不要」「不需要」「取消」等，需要确认没有被截断 |
| **两人重叠** | 声纹检测到多个说话人重叠 |

#### 4.19.2 二次识别策略

```text
第一遍：本地 SenseVoice（快速，<200ms）
    ↓ 命中触发条件？
    否 → 直接进入清洗层，正常流程
    是 ↓
第二遍：用更强模型 or 云端 ASR
    • 更强本地模型（非量化 SenseVoice，速度稍慢但准确率更高）
    • 云端 ASR（精度最高，有延迟 + 隐私成本，仅高风险时使用）
    ↓
两遍结果合并（取置信更高者 or 用 Lexicon 校验哪个更合理）
    ↓
进入清洗 + 实体纠错层
```

#### 4.19.3 不同场景下的 fallback 策略

| 场景 | 推荐策略 |
|------|---------|
| **普通闲聊** | 本地识别即可，不触发二次 |
| **高风险任务（发消息/删文件）** | 二次识别 + 执行前确认（双重保险） |
| **本地输出疑似乱码/低置信** | 触发云端 ASR fallback |
| **云端不可用（网络离线）** | 回退本地 + 标记 `low_confidence`，触发用户重说提示 |

**成本控制**：不建议全量走云端（延迟增加 500ms～2s、有隐私风险、有费用）；**只在高风险 + 低置信时按需触发**，日常使用绝大多数请求走本地一遍即可。

**与 §4.15 STT 引擎评估的关系**：
- §4.15（Phase 16）是「考虑整体换 STT 引擎」
- §4.19（Phase 0-C）是「在现有引擎上加高风险二次复核」
- 两者**不互斥**：二次识别是应急补丁，引擎评估是中长期决策

**Phase 0-C 交付物**：
1. 触发条件判断模块（置信分 + 意图风险分类）
2. 二次识别调用接口（本地强模型 + 云端 ASR fallback 开关）
3. 两遍结果合并策略

### 8.3 必须测真实录音链路（不能只用文字用例）

> **Codex 要求**：Eval 不能停留在方案层，**必须落成具体脚本和固定样本集**，否则每次只能靠手动复测，无法持续回归。

| **T0-CN 中文** | 纯中文句子 → IO 路由 | 回归否定词保护、同音混淆 | `eval/t0_chinese_cases.jsonl`（§4.18，≥50 条）|

| **T2 桌面 PTT** | Tauri PTT 录音 → JVS → 全链路 | 含重采样、真实麦克风 | `scripts/test_jvs_voice.py` + `data/eval_wav/t2_ptt/`（≥10 条）|

**固定样本集要求**：

## 9. 落地避坑（Watch-outs）

方案逻辑成立，但写代码时有 **两个高频翻车点**：

### 9.1 极度警惕：LLM 洗衣机 C — 延迟雪崩 + 自由重写事故

| 风险 | 说明 |
|------|------|
| **延迟雪崩** | 把 L3 同款 **大模型**（如 Qwen3.5-Plus）拿来跑 500ms 预算的纠错层 → 纠错 alone 可能 +1～3s |
| **自由重写事故** | LLM 返回整句改写文本，把 message 正文里的 luck 改成 Lark → **比不纠错更糟**（§4.3 Codex 红线） |

**硬性对策**：

```text
手术 C 启动（小模型，结构化 JSON 输出 only，max_tokens 极简 prompt）
    ↓
  等待，上限 500ms（可配置，建议默认 400ms）
    ↓ 超时 / 报错 / 模型未加载 / 输出非 JSON
立即降级：手术 B + Lexicon（<20ms），标记 correction_fallback=timeout
    ↓
external 操作：强制轻确认（因未过 LLM 确认）
```

**DoD**：
- 监控 `correction_latency_ms`；P99 < 500ms
- LLM 输出 **100% 结构化 JSON**；`message_body` 槽 **代码层硬拦截**
- timeout 降级率可观测；external 必确认

**人话**：洗衣机 C 是 **厨房里的迷你洗碗机**，不是 **把整个 L3 厨房再洗一遍**；更不是 **帮用户改稿的编辑器**。

### 9.2 统一实体库必须有「保鲜」同步，不能靠手改 JSON

| | 说明 |
|---|------|
| **坑** | 第二步做完一个 `entities.json`，上线时很准；三个月后同事换了、项目改名了，**luck 仍映射 Lark 但 Vivian 已离职** |
| **后果** | 纠错脑子基于过期世界，越用越错；手动维护 JSON 成为灾难 |
| **对策** | 实现实体库时 **预留同步接口**，SSOT 由脚本刷新，人只审异常 |

**推荐同步时机**：

| 触发 | 数据源 | 更新内容 |
|------|--------|---------|
| **JVS / Desktop 冷启动** | 本机已安装应用、注册表 DisplayName | `apps` 增量 |
| **用户每日首次登录** | 飞书 API 通讯录 **增量** | `contacts` 增删改 |
| **用户改设置 / 确认纠错** | 个人别名、反馈样本 | 个人 Lexicon 覆盖 |
| **定时（默认 6h）** | 项目/群组 MCP | `projects` |

**接口形态（本方案交付范围）**：

```text
lexicon_sync.sync_apps()      ← 扫描本机，merge 进 SSOT，不删用户自定义别名
lexicon_sync.sync_contacts()  ← 飞书增量，离职 contact 标记 inactive 而非硬删历史映射
lexicon_sync.export_for_stt() ← 供热词 A、纠错 B/C 消费的精简视图
```

**原则**：同步 **追加与标记**，别每次全量覆盖把用户教过的别名冲掉；同步失败 **降级用上次快照**，打 `[LexiconSync]` 日志，不阻塞语音。

## 11. 小结

**表面现象**：要发 Lark 消息，却去打开 luck.exe。  
**本质**：**别只换 STT 耳朵**——中英混说里 ASR 错一个实体 Agent 就歪；缺的是 STT 后的 **纠错脑子**（实体规范化）。

**方案定位（Codex）**：作为 **「端到端语音任务鲁棒性方案」** 合理且基本够完整；若问题仅是 **「STT 字面准确率」**，还需配合音频链路 / 热词 / 二次识别——纠错层解决的是 **听错后任务还能做对**。

| 缺失 | 应对 | 交付层 |
|------|------|--------|
| STT 原稿直连 Router | 规则 B + Lexicon（Phase 3） | **MVP** |
| 正文 luck 被改成 Lark | **禁改 message 槽**（铁律）；LLM **只输出结构化实体建议**（§4.3） | **MVP** |
| 发消息静默执行 | **外部副作用必须确认** | **MVP** |
| FileNotFoundError 透传 | 人话澄清（Phase 1） | **MVP** |
| 缺 recipient/message 仍 execute | 槽位门禁（Phase 4） | **MVP** |
| 两个 Vivian 硬猜 | 来源优先级 + 澄清 | MVP / 增强 |
| Router 好了工具仍炸 | 工具层同 Lexicon | **MVP** |
| LLM 自由重写整句 | 结构化 JSON only + message_body 硬拦截（§4.3、§9.1） | 增强 |
| 只测文字不测录音 | T0～T4 真实音频 Eval（Phase 15） | 增强 |
| VAD / 声纹截断 | 前置链路诊断（Phase 0-A） | 增强 |
| 高风险操作误识别 | 二次识别（Phase 0-C） | 增强 |
| Eval 停在方案层 | 固定样本集 + 自动化脚本 | MVP 先 30 条 → 增强自动化 |

> **Codex 交付建议**：**先行 MVP**（30 条样本 + Lexicon + luck/viian 纠错 + 禁改正文 + 槽位门禁 + 发消息确认 + 不透传 FileNotFoundError）**可先上线**；**后续增强**（T1～T4 Eval、热词、二次识别、LLM、主动教导、换引擎）按 §7.0 逐步补齐。**完整方案没有砍掉任何模块**。

**一句话**：听成 luck / v薇m **可以接受**；**先 MVP 止血、再增强补全**；**发消息必须问一声**；**正文里的 luck 不是 Lark**；**LLM 只建议实体，不改整句**。
