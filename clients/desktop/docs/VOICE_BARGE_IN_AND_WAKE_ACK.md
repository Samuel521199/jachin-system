# 语音打断与唤醒应答 — 设计说明

> **状态**：主功能已落地（随时开口打断、唤醒后说「我在」、60 秒连续对话）  
> **一句话**：你喊醒 Jachin 后，它应答应一声；它说话或想事情时，你随时开口就能让它停下并听你讲。  
> **相关文档**：`VOICE_WAKE_ARCHITECTURE.md`（怎么被唤醒）、`VOICE_COMPANION_MODULE_PLAN.md` §7.3（陪伴语音总方案）

---

## 1. 要解决什么问题？

大家用语音陪伴时，最常吐槽两件事：

| 你的感受 | 理想体验 |
|----------|----------|
| 它还在念回复，我继续说，它完全不理我 | 我一开口，它马上停，专心听我说什么 |
| 喊完唤醒词只有「滴」一声，不知道有没有在听 | 喊完后它应一声「我在」或「嗯」，像真人在旁边 |

以前的问题大致是：朗读时麦克风被关掉或没在听、唤醒后没有口头应答、想打断只能再喊一遍唤醒词。这份文档规定**应该怎样**，代码按这里实现。

---

## 2. 完整对话流程（用户视角）

想象你和 Jachin 面对面聊天：

```text
1. 你喊唤醒词（例如「快来听我说话」）
   → 一声短「滴」
   → 它应一句：「我在」「嗯」或「有什么可以帮你」（随机，避免每次同一句）
   → 小圆球变绿，表示在等你说话（不是黄色「正在回答」）

2. 你说正事（例如「今天天气怎么样」）
   → 它去想、去答，可能会朗读回复

3. 对话窗口约 60 秒内
   → 不用重复喊唤醒词，可以直接问下一句
   → 它念的时候你也可以随时开口打断

4. 超过 60 秒没再有效对话
   → 回到「门卫」：只有再说唤醒词才会理你（防环境杂音误触发）
```

**如果它正在长篇朗读时你又喊了唤醒词**：先让它闭嘴，再「滴」+ 答应一声，再听你新指令——不能先答应再闭嘴，否则会叠音。

---

## 3. 三条基本原则

1. **你的话优先**  
   它在答应、朗读或思考时，你有效开口 → 立刻停声、别播后面的句子、别继续想上一题，改听你这句。

2. **打断不必再喊唤醒词**  
   已经聊起来了，直接说话就能打断；再喊唤醒词只是备选，不是唯一方式。

3. **麦克风不能「聋」**  
   它在说话时，麦克风仍开着听你有没有开口；但会避免把它自己的声音当成你的话（见下文「防自听自译」）。

**体验目标（尽量做到，不是硬保证）**  
- 你感觉它闭嘴 + 圆球变绿：大约 **0.1 秒内**  
- 后台停合成、停思考：可以稍慢到 **1 秒内**；就算慢了，也不会突然又冒出上一句的尾音

## 4. 唤醒后的「我在」怎么弄？

### 4.1 三种声音，别混

| 是什么 | 什么时候 | 从哪来 |
|--------|----------|--------|
| **滴一声** | 刚被唤醒 | 固定短提示音 |
| **口头答应**（「我在」「嗯」等） | 滴声之后 | **事先存好的本地音频**，不找大模型现生成 |
| **正式回答** | 你说完指令之后 | 大模型 + 语音合成 |

为什么答应声不能现生成？现生成至少要半秒到一秒，像反应很慢；本地音频才能「秒应」。

### 4.2 可以在设置里改

在控制台 **唤醒模式 → 唤醒确认**：

| 设置 | 含义 |
|------|------|
| 仅滴声 / 仅口头 / 滴声+口头 | 默认：滴声+口头 |
| 自定义一句 | 填了就用这一句（需先生成音频文件） |
| 不填自定义 | 从池里随机：我在 / 嗯 / 有什么可以帮你 |

配置存在 `UserSettings`：`wake_ack_mode`、`wake_ack_phrase`、`wake_ack_pool` 等。

### 4.3 音频文件从哪来？

首次使用需用 JVS 批量生成（与正文朗读同音色）：

```powershell
python scripts\gen_wake_ack_wavs.py
```

会写到：
- 项目里 `clients/desktop/public/audio/wake_ack/`（打包用）
- `%LOCALAPPDATA%\jachin\desktop\audio\wake_ack\`（本机直接用）

没有对应文件时：**只播滴声，不报错、不卡住**。

### 4.4 答应期间圆球什么颜色？

**绿色（在听）**，不要变黄（在答）。黄灯容易让人以为它已经在回答正题了。

### 4.5 防「自听自译」

它在出声时（滴声、答应、朗读），麦克风仍采集，但：

- **不会**把这段声音送去识别成你的话  
- 打断检测阈值会抬高一点，减少喇叭漏音误触  
- 暂停「唤醒词门卫」轮询，避免它自己说的话触发唤醒  

你开口打断后，立刻解除屏蔽，从当前开始认你的话。

## 5. 怎么打断它？（三种方式，任选其一）

| 方式 | 怎么做 | 适合什么时候 |
|------|--------|----------------|
| **直接说话**（主方式） | 连续说大约 0.2～0.3 秒以上 | 日常：觉得它啰嗦，直接说新题 |
| **再喊唤醒词** | 在它说话或思考时再喊一遍 | 习惯「喊名字打断」的人 |
| **按键 / 点圆球** | **Ctrl+Space**，或朗读/思考时 **单击 Orb** | 环境吵、或就是想让它闭嘴 |

**注意**：
- 还没唤醒、处于「门卫」时：随便说话 **不会** 进门，只有唤醒词才行（防杂音）  
- 已经聊起来了（60 秒窗口内）：直接说话即可，不必再喊唤醒词  
- **不能**只靠「音量变大」判断打断——喇叭回声会让它误以为自己被打断

---

## 6. 打断时系统在干什么？（四步急停）

可以记成：**闭嘴 → 作废排队 → 停合成 → 停思考 → 开始听新句**

| 步骤 | 人话 | 技术动作（给开发看） |
|------|------|----------------------|
| 1 | 立刻闭嘴 | 前端淡出停播 + Rust 停系统扬声器（两边都要停） |
| 2 | 后面的句子别播了 | 更新播放「代次」，在途语音丢弃 |
| 3 | 别继续合成了 | 通知 JVS 取消当前会话合成 |
| 4 | 别继续想了 | 通知 L3 中止当前回答 |
| 5 | 开始听你说 | 圆球变绿，清空缓冲，解除「自听自译」屏蔽 |

**答应声被打断**：不补播「我在」，你接着说的就算正式指令。  
**思考中被打断**（还没出声）：同样要停思考；界面上半截字可标「已中断」。  
**网络慢**：只要已经闭嘴，迟到的旧语音也不会再冒出来。

**止音别太硬**：约 50～100ms 音量渐弱再停，避免「啪」一声爆音；圆球变绿和渐弱同时进行。

## 7. 连续对话（60 秒窗口）

| 规则 | 说明 |
|------|------|
| 时长 | 唤醒成功后 **60 秒** 内可直接接着问 |
| 续期 | 每轮你的话识别成功，再 **+60 秒** |
| 窗口内 | 可随时开口打断，不用唤醒词 |
| 窗口外 | 又要先说唤醒词 |
| 窗口到了但它还在念 | **不强行掐断** 当前这句；念完后才回到「只听唤醒词」 |

## 8. 状态流转（简化）

```text
等唤醒词 ──喊醒──→ 滴 + 答应 ──→ 绿灯等你说话 ──→ 识别你的指令
                                              ↓
                                    思考 → 朗读回答
                                              ↓
                         你说话 / 快捷键 / 再喊唤醒词 / 点圆球
                                              ↓
                                    急停 → 绿灯听你新话
                                              ↓
                         60 秒内可继续；超时回到「等唤醒词」
```

## 11. 怎么验收？

1. 喊唤醒词 → 有滴声 + 本地「我在/嗯」（不是等大模型生成）  
2. 它答应或朗读时你开口 → 约 0.1 秒内听感上闭嘴，圆球变绿  
3. 闭嘴后 1 秒内开始认真听你的新话  
4. 它思考中你开口 → 思考停止，不会又播旧回复  
5. 60 秒内不用重复唤醒词；超时后需再喊  
6. 它自己的声音不会出现在识别结果里  
7. 设置改完，下次唤醒即生效  
8. 连续打断 5 次：无爆音、无尾音  
9. 没有 WAV 文件时：只有滴声，流程不卡  

**手动试一遍**：

```text
唤醒 → 答应 → 中途说话打断 → 新话有回复
长篇朗读中说话 → 很快停 → 新话生效
长篇中再喊唤醒词 → 先停 → 再答应 → 再说指令
Ctrl+Space → 停 + 绿灯
```

## 13. 常见边界情况

| 情况 | 怎么办 |
|------|--------|
| 一秒内连打断好几次 | 每次都完整急停；短冷却防连触 |

## 14. 附录：打断后「听不见用户」— 问题与方案

> **背景**：联调脚本与桌面端均可能出现——打断成功了（日志有 `[打断] 人声(VAD)`），但用户觉得「它不理我了」。本节用日志里的真实序列说明根因，并给出统一修复方案（脚本 + 桌面共用原则）。

### 14.1 你看到的日志在说什么？

```text
[指令 STT] 不要跟我说这个😔        ← 第二轮指令已送进 L3
[L3] 思考中…（此时说话可打断）
[打断] 人声(VAD) → …               ← 你说话触发了打断（可能出现两次）
[打断] 人声(VAD) → …
[L3] 已打断，丢弃本轮
（之后没有新的 [指令 STT]）        ← 问题：打断后没再识别到你的新话
```

说明三件事：

1. **打断链路是通的**（能停思考 / 停播）
2. **触发打断的那句人声，没有变成「新指令」**
3. **TTS 播放失败**（`winsound 启动失败`）时，你只能在「思考中」打断——更容易踩到下面说的坑

### 14.2 根因（人话版）

| 根因 | 人话 |
|------|------|
| **思考中不让采指令** | L3 在算的时候，为不乱接话，系统往往 **暂停「截句送 STT」**；你的话只拿去判断「要不要打断」，**不进指令缓冲区** |
| **打断时清空缓冲** | 一触发打断就 `reset` 截句器 + 清空音频队列 → **你正在说的前半句被扔掉** |
| **一句话两件事** | 同一段人声既要触发打断，又应该是新指令；当前实现往往 **只做前者** |
| **连触两次打断** | 同一次开口触发两遍急停，状态被反复清空，更难接上后半句 |
| **播不出声仍挡截句** | TTS 失败时虽无喇叭声，但「思考中」仍占着 `busy`，截句仍被挡住 |

**用户体感**：「我明明在说话，它停了，但又不理我」—— 不是麦坏了，是 **打断与采指令两条路没接上**。

### 14.3 目标行为（产品定义）

打断完成后，系统应进入 **「重新听你说」** 相位（`LISTENING`，可细化为 `LISTENING_REARM`）：

1. 圆球 **绿灯**（或脚本打印 **「请说新指令」**）
2. **立刻** 允许截句，不等 L3 线程完全退出（`run_abort` 可异步）
3. **触发打断的这段人声**：从打断确认时刻起，应 **并入新指令**（至少保留打断前约 0.5～1s 环形缓冲，避免句首被切掉）
4. **同一次开口只急停一次**（冷却约 300～500ms，防日志里双行 `[打断]`）
5. 若打断后 **8 秒内没有有效新话**，回到安静等待（对话窗口内仍可不喊唤醒词）

### 14.4 方案：打断后听感恢复（Listen Recovery）

与「四步急停」并列，打断后增加 **第五步：重新武装耳朵**（实现上可与急停并行）。

```text
用户开口（思考中 / 朗读中）
  → 检测到连续人声 → 进入 BARGE_IN（瞬态）
  → 四步急停（闭嘴、作废排队、停合成、停思考）
  → 【第五步】LISTENING_REARM：
       a. 结束 Masking / 解除 busy 门闩（允许截句）
       b. 截句器 reset，但带上「打断前环形缓冲」拼进新句
       c. 打断检测器 reset + 冷却 300～500ms（禁止连触）
       d. Orb 绿 / 日志：「已打断，请说新指令」
       e. 可选：极短滴声（与答应声不同），仅提示「现在轮到你说」
  → 截句有效 → STT → 新一轮 L3
```

**与现有设计的关系**：不推翻 §5.2 四步急停，只在第 5 步把「竖起耳朵」写细，避免只做 `reset` 却不 **接话**。

### 14.5 思考中打断 vs 朗读中打断

| 场景 | 打断时 | 打断后采指令 |
|------|--------|----------------|
| **朗读中** | 先止音，Masking 解除 | 从当前帧起截新句；喇叭尾音不进 STT |
| **思考中（无声）** | `run_abort`，丢弃在途回复 | **关键**：触发打断的语音要进截句器，不能只触发急停 |
| **思考完刚要播、TTS 失败** | 无喇叭声，等同思考中 | 同样走思考中规则；勿因无播放漏接话 |

### 14.6 防双触与「半句话」

**防双触**（对应日志里两行 `[打断]`）：

- 一次有效人声事件 → **只执行一轮** `BARGE_IN`
- 急停完成后 **300～500ms 内** 忽略新的打断检测（冷却）
- `run_abort`、JVS cancel **幂等**（重复调没关系）

**半句话 / 句首被切**（如说「我不需要你了」却只识别「不需要你了」）：

- 麦克风线程 **始终** 保留最近约 **2s** 环形缓冲
- 打断时：用 **更低门限** 在缓冲里找说话起点，并再 **往前多留 ~300ms**（pre-roll），整段拼进截句器
- 打断确认那一帧 **不要重复喂也不要丢**（已在缓冲末尾）
- 接话阶段截句门限略低于平时，照顾起首轻声字（如「我」）

这样用户边打断边说的整句能进 STT，而不是只剩后半截。


### 14.8 验收标准（打断后能听清）

1. 思考中用户说「算了，问别的」→ 打断后 **同轮或下一轮** STT 能识别该句（或其中有效部分）
2. 朗读中用户开口 → 止音后 **1 秒内** 新句进 STT
3. 日志中 **一次开口至多一条** 打断记录（冷却内不重复）
4. 连续「打断 → 说新话 → 再打断」3 次，每次都能接到新指令
5. TTS 播放失败时，思考中打断仍满足 1～3（不依赖喇叭）

### 14.9 实施分期（建议）

| 阶段 | 内容 |
|------|------|
| **P2c** | `LISTENING_REARM`：打断后放开截句、环形缓冲、防双触、用户提示文案 |
| **P2d** | 测试脚本对齐 P2c；修 Windows TTS/答应播放（与打断门闩解耦） |
| **P3** | 思考中「边打断边说的整句」与嘈杂环境压测 |

---

**本节一句话**：打断不仅要「让它闭嘴」，还要 **把用户用来打断的那句话（或紧接的半句）接上**；否则用户会觉得「打断了反而更不理我」。
