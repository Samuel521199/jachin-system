# HR 招聘智能助手 - 产品设计文档

> 面向 HR 团队的产品说明，帮助理解项目目标、功能与使用方式

---

## 一、产品概述

### 1.1 我们解决什么问题？

招聘过程中，HR 常面临：

- **海量简历**：Boss 直聘等平台每天产生大量推荐、主动投递，人工逐份筛选耗时且易遗漏
- **标准不一**：不同 HR 对同一份简历的判断可能不一致，缺乏统一、可追溯的评估标准
- **重复劳动**：打招呼、催收简历、归档 PDF 等流程高度重复，占用大量时间
- **隐私风险**：简历含手机号、身份证等敏感信息，直接交给 AI 存在合规隐患

### 1.2 产品定位

**HR 招聘智能助手** 是一套基于 AI 的招聘筛选与流程自动化系统，旨在：

1. **自动化日常巡逻**：定时抓取简历、粗筛、自动打招呼、收网 PDF，减少人工重复操作
2. **多专家联合评审**：用「技术专家 + HR BP + 主理法官」三视角对简历进行结构化评估，输出统一、可解释的结论
3. **隐私合规**：在 AI 处理前对敏感信息脱敏，满足数据安全要求

## 二、核心价值

| 价值点 | 说明 |
|--------|------|
| **提效** | 雷达粗筛 + 自动打招呼 + 收网归档，将大量重复工作交给系统，HR 专注高价值沟通与决策 |
| **标准化** | 三专家评审模型，输出结构化结论（技术分、HR 分、综合简报），减少主观偏差 |
| **可追溯** | 每份简历的评审意见、辩论过程可留存，便于复盘与改进 |
| **合规** | 简历在进入 AI 前自动脱敏，降低隐私泄露风险 |

### 3.2 第一层：雷达粗筛与撒网

**触发**：系统每 30 分钟自动执行一次（可配置）

**做什么**：

1. 从 Boss 直聘抓取「推荐牛人」「搜索人才库」「主动打招呼的求职中」中的在线简历
2. 用轻量 AI 做**底线过滤**：学历、工作年限等硬性条件不达标者直接剔除
3. 对达标者**自动发送打招呼**：「您好，我们对您的经历很感兴趣，方便发一份简历过来吗」
4. 对主动打招呼的候选人，回复「方便发一份简历过来吗」催收 PDF

**HR 收益**：不用手动刷推荐、逐条打招呼，系统自动完成初筛与触达。

---

### 3.3 第二层：意向确认与收网归档

**触发**：与第一层并行，每次巡逻时一并检查

**做什么**：

1. 扫描消息列表，识别已回复、有意向的候选人
2. 下载候选人发送的 PDF 简历附件
3. 将 PDF 保存到「待评审」文件夹（`pending`）
4. 更新招聘状态看板（如：待审 PDF 数量）

**HR 收益**：PDF 自动归集，无需手动下载、重命名、分类。

---

### 3.4 第三层：诸神黄昏 - 多专家评审

**触发**：满足以下任一条件时自动执行

- **满载**：待评审 PDF 数量达到 50 份（可配置）
- **定时**：到达每日指定时间（如 08:30），做「早报式」批量评审

**做什么**：

1. 读取「待评审」文件夹中的 PDF
2. **脱敏**：手机号、身份证等敏感信息在进入 AI 前被替换为占位符
3. **三专家评审**：
   - **技术总监（Agent A）**：评估技术栈匹配、项目含金量、工作年限
   - **HR BP（Agent B）**：评估稳定性、沟通能力、自我评价逻辑
   - **主理法官（Agent C）**：综合 A、B 意见，给出最终 Pass/Reject 及结构化简报
4. 通过名单同步到飞书（Lark）多维表，便于安排面试
5. 已评审 PDF 移至「已处理」文件夹

**HR 收益**：获得结构化、可解释的评审结论，减少主观判断，便于与业务部门对齐。

## 四、零阶漏斗：自然语言发帖与规则定调（上行）

### 4.1 功能说明

HR 可在**飞书（Lark）**中直接发送自然语言招聘要求，系统自动解析、生成 JD、保存评审规则并准备发布。

**示例**：
- 「帮我发个前端的岗，15-20k，必须统招本科，不要频繁跳槽的」
- 「招个 Java，20k，只要统招本科，要有大厂外包经验也行」

### 4.2 执行流程

1. **解析**：AI 将自然语言解析为结构化 JD（岗位名称、薪资范围、评审规则 hr_criteria）
2. **烙印规则**：将 `hr_criteria` 保存到 `~/.jachin/workspace/hr_rules/` 和 `recruitment_status.json`
3. **发布准备**：JD 保存到 workspace，供 Boss 直聘发布（当前为手动发布，后续可扩展自动发布）
4. **多 Agent 依据**：小脑粗筛（brain_filter）与三专家评审（tribunal）均依据此 `hr_criteria` 分析候选人是否符合

### 4.3 飞书端体验

- HR 发消息 → 系统回复：「收到指挥官。JD 已生成并发布至 Boss 直聘；『必须统招本科』等规则已烙印至评审中枢。狩猎已开始。🚀」

## 五、全天候雷达：实时进度汇报（下行）

### 5.1 汇报模式

| 模式 | 触发 | 说明 |
|------|------|------|
| **主动推送** | 里程碑（10/20/30... 份 PDF）或每日 18:00 | 系统自动向飞书发送进度卡片 |
| **被动查询** | HR 在飞书问「现在几个了？」「前端岗收了多少简历？」 | 系统读取 recruitment_status 并回复 |

### 5.2 进度卡片内容

- 🎯 目标进度：待审 PDF 数 / 目标数（如 12/50）
- 📡 雷达扫描：已阅览在线档案数
- 💬 沟通转化：打招呼数、已提交附件数
- 📋 累计已审：历史已评审 PDF 数
- 预计明早 8:30 触发首轮多 Agent 交叉评审

### 5.3 被动查询示例

HR：「现在几个了？」  
系统：「报告，目前刚刚突破 10 份大关！我们已经给 30 个匹配度极高的人打了招呼，等他们晚上下班回复，明早库房绝对充实！」

## 七、Lark 多维表格输出与面试安排

### 7.1 多维表格输出格式

多 Agent 筛选出的候选人以**表格形式**输出到 Lark 多维表格中：

| 列 | 说明 |
|----|------|
| 排名 | 从上至下按推荐程度排序（第 1 名最推荐） |
| 候选人信息 | 姓名、联系方式等基础信息 |
| 推荐理由 | 三专家综合简报（brief），说明为何推荐 |
| PDF 附件链接 | 简历 PDF 的本地或云端链接，便于 HR 快速查看 |

### 7.2 实时更新机制

- 多维表格中的 **Top 10 最终推荐候选人** 信息为**实时更新**
- 每次终局审判执行后，系统会刷新表格内容，确保 HR 看到的始终是最新推荐名单
- 若新评审结果中推荐度更高的候选人出现，会替换原有排名

### 7.3 面试安排流程

1. **人工选取**：HR 在 Lark 多维表格中**手动勾选**要安排面试的候选人
2. **AI 安排**：选取完成后，由 AI 根据 HR 的选择，自动安排面试时间、发送通知等后续流程

> 设计原则：AI 负责筛选与推荐，人工负责最终面试决策；面试安排由 AI 执行，提升效率。

## 八、三专家评审模型

### 8.1 为什么是「三专家」？

单一 AI 容易产生偏见或遗漏。我们采用**三权分立**设计：

| 专家 | 角色 | 关注点 |
|------|------|--------|
| **Agent A** | 技术总监 | 技术栈匹配、项目含金量、工作年限、逻辑深度 |
| **Agent B** | HR BP | 稳定性、沟通能力暗示、自我评价逻辑、情商均衡 |
| **Agent C** | 主理法官 | 综合 A、B 意见，做最终裁决，输出结构化简报 |

### 8.2 评审流程

1. **第一轮**：A、B 各自独立阅读简历，给出 Pass/Reject 及理由
2. **第二轮（如有分歧）**：A、B 互相质询、辩论
3. **第三轮**：C 综合辩论记录，给出最终结论和简报

### 8.3 输出示例

每份简历输出包含：

- **verdict**：Pass / Reject
- **tech_score**：技术维度评分
- **hr_score**：HR 维度评分
- **brief**：综合简报（供 HR 快速了解候选人）
- **agent_a_opinion**：技术总监意见
- **agent_b_opinion**：HR BP 意见

## 九、使用方式

### 9.1 日常使用（自动化）

配置好定时任务后，系统自动执行：

- **每 30 分钟**：雷达粗筛 + 收网归档
- **每日 08:30**（或待审满 50 份时）：批量评审 + 飞书同步

HR 只需定期查看飞书多维表中的 Top 10 推荐名单（按推荐程度排序，含推荐理由和 PDF 链接），手动选取要面试的候选人后，由 AI 安排面试。

### 9.2 手动运行（按需）

也可手动触发：

```bash
# 日常巡逻（雷达 + 收网）
python scripts/cron_runner.py --patrol --job "Java开发"

# 强制终局审判（无视触发条件）
python scripts/cron_runner.py --force-judge --lark-sheet "xxx"
```

### 9.3 本地简历评审

若有本地 PDF 简历，可直接运行：

```bash
python main.py run --source local --files "简历1.pdf" "简历2.pdf" --job "Python工程师"
```

## 十、数据与隐私

### 10.1 脱敏机制

在简历进入 AI 评审前，系统会：

- 将手机号、身份证号等替换为占位符
- 仅将脱敏后的文本交给 AI 模型
- 原始 PDF 保留在本地，不上传

### 10.2 数据存储

- 简历 PDF：存储在本地 `~/.jachin/workspace/resumes/` 下
- 评审结果：以表格形式同步到飞书多维表（按推荐程度排序，含推荐理由和 PDF 链接），Top 10 实时更新，供 HR 手动选取面试候选人后由 AI 安排面试
- Cookie（Boss 直聘）：仅存本地，零密码上云

## 十二、典型场景

### 场景 1：日常招聘

HR 发布 Java 开发岗位，系统每 30 分钟自动抓取推荐牛人，粗筛后自动打招呼；候选人回复并发送 PDF 后，系统自动收网归档；待审满 50 份或每日 08:30，批量评审，通过名单以表格形式同步飞书多维表（按推荐程度排序，含推荐理由和 PDF 链接，Top 10 实时更新）；HR 在表格中手动选取要面试的候选人，后续由 AI 安排面试。

### 场景 2：紧急补位

业务部门急需补人，HR 从本地或 Boss 导入一批简历，手动运行 `main.py run`，立即获得三专家评审结果，快速筛选候选人。

### 场景 3：标准对齐

HR 与业务部门对「什么样的人算合格」有分歧，可调出历史评审记录（Agent A、B、C 的意见），作为讨论依据，逐步沉淀成可复用的招聘规则。
